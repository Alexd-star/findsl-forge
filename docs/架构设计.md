# 架构设计

## 1. 设计目标

正式编译器需要同时解决四类问题：语法覆盖、金融语义正确、Doris 物理性能和可配置扩展。最合适的结构不是继续在旧字符串管道上增加条件分支，而是采用编译器分层：每层只处理一种决策，层间通过不可变对象传递，所有转换都可诊断和测试。

```text
DSL 文本
  -> Frontend
  -> Typed AST
  -> Domain Binding
  -> Logical IR
  -> Logical Optimizer
  -> Physical Planner
  -> Doris Backend
  -> Validation / Execution / Evidence
```

## 2. 各层职责

| 层 | 输入 | 输出 | 核心文件 |
| --- | --- | --- | --- |
| Frontend | DSL 文本 | AST、源位置、语法诊断 | `official/frontend/`、`grammar/OfficialSlot.g4` |
| 类型与语义 | AST、注册表、编译上下文 | Typed AST、领域对象 | `typed_ast.py`、`semantics.py`、`domain/` |
| Logical IR | 领域对象 | 与数据库无关的关系计划 | `lowering.py`、`ir/` |
| 逻辑优化 | Logical IR | 等价且规范化的 Logical IR | `optimizer/engine.py`、`optimizer/rules.py` |
| 物理规划 | Logical IR、统计、策略目录 | 物理候选、成本、风险、最终计划 | `physical/` |
| Doris 后端 | Physical IR、物理目录 | SQLGlot AST、Doris SQL | `backend/doris.py`、`backend/temporal_sql.py`、`backend/ranking_sql.py` |
| 校验执行 | SQL、目录、Doris 连接 | 结构校验、结果、EXPLAIN/Profile | `backend/validation.py`、`backend/executor.py` |
| 证据 | 编译/执行结果、版本信息 | 正确率、性能、快照和合同结论 | `correctness.py`、`performance.py`、根包 evidence 模块 |

## 3. 为什么这是当前最佳主线

- ANTLR4 复用成熟解析器生成器，文法是唯一事实源，避免正式语法继续由手写分支扩散。
- Typed AST 在进入关系计划前消除字符串歧义，使函数参数、日期、比较和集合类型能够静态检查。
- Canonical Logical IR 把业务含义与 Doris 表布局分离；同一语义可选择普通扫描、窗口、前缀、技术特征或分区汇总路径。
- 等价规则与成本选择分离。规则负责“哪些计划含义相同”，成本模型负责“当前数据上选哪个”，避免为了跑分快而改变语义。
- SQLGlot 构造 SQL AST，减少手工拼接导致的注入、引用和括号错误。
- Doris 自身的 Nereids、分区裁剪、统计和物化能力继续由数据库负责，项目不重复实现通用数据库优化器。

## 4. 编译主入口

`findsl.official.pipeline.compile_official` 负责串联正式阶段。`OfficialPipelineOptions` 控制 strict/recovery、数据配置和物理策略；`OfficialPipelineResult` 返回 AST、Logical IR、优化轨迹、Physical IR、SQL 和诊断。阶段错误统一转为带错误码、位置和部分结果的 `OfficialPipelineError`。

Web、CLI 和 API 应调用这一入口，不应直接绕过 binder、IR 验证或 SQL 校验。

## 5. 旧管道边界

根包中的 `lexer.py`、`parser.py`、`semantic.py`、`sqlgen.py`、`compiler.py` 和 `official_slot.py` 仍服务于兼容样例、差分测量及少量内部工具。它们不是新功能入口。`pyproject.toml` 中的 import-linter 合同禁止 `findsl.official` 依赖旧模块，防止重构倒退。

立即删除旧管道会失去迁移基线和部分兼容行为；继续向其中增加官方语义又会形成双主线。正确做法是保持隔离，待正式编译器覆盖、调用统计和差分门禁连续稳定后，再按模块移除。

## 6. 声明式扩展

配置层管理指标映射、函数签名、资源表、物理策略、范围政策和外部来源。配置必须通过 schema 和类型验证，模板只能使用受控表达式节点，禁止在配置中注入任意 SQL。

新增指标的理想流程是：增加目录项、字段来源和测试，不修改编译核心。新增函数分两类：

- 可由现有类型化算子组合的新函数，通过 `expression_template` 受控表达式树扩展，不改 parser、binder、planner 和 backend 分支。模板加载时检查类型、参数、节点数和深度，禁止原始 SQL。
- 引入全新关系语义的函数，需要增加新的 typed operator 和 lowering/physical/backend 支持。赛题所说“零核心改动”应通过插件协议或受控模板覆盖可声明类别，不能承诺任意新语义都只靠配置完成。

## 7. 物理优化

Physical Planner 针对金融 DSL 生成有限候选：普通事实表扫描、窗口计算、前缀差分、技术特征表、最新快照、分区汇总和可用外部范围连接。候选携带估算行数、分区数、特征新鲜度、可解释风险和预估成本；先淘汰语义或水位不安全的方案，再在可行候选中选择成本最低者。

编译路径不应实时访问 Doris 获取统计，否则会破坏 P95 和可用性。统计通过离线刷新和带版本的目录进入编译上下文；运行时 EXPLAIN/Profile 用于证据与反馈，不作为每次编译的强依赖。

## 8. 安全与正确性边界

- 输入长度、语法深度、候选数和执行资源必须有限额。
- SQL 输出必须经过允许表、列和函数的 AST 级校验。
- 外部数据缺失、过期或来源不完整时 fail closed。
- LLM 只能生成候选 DSL 或解释文本，不能跳过确定性编译器直接执行 SQL。
- 等价验证使用独立 reference SQL 或独立解释器，不能复用被测规划器生成期望结果。
