## 3. 历史证据的使用方式

历史结果可能真实，但通常对应不同 Git HEAD、配置或数据快照。引用时至少同时给出：

- 证据生成时间；
- Git HEAD；
- 官方工作簿或输入数据 SHA-256；
- 配置/目录 fingerprint；
- Doris 版本、表行数和数据日期；
- 工作负载定义和计时口径。

缺少这些字段的历史数字只能作为线索，不能进入当前评分结论。`40.52x`、`36.24x`、`13.99x`、`1.393x` 等结果属于不同工作负载，不能相互替代或挑选最高值作为统一加速比。

| --- | --- | --- |

| `reports/` 中旧阶段报告 | 标记 historical 或重新生成。 | 不被当前 metadata/manifest 引用。 |

## 5. 代码归档与删除门禁

旧编译管道暂不删除。它仍承担兼容入口、内部 FinDSL 样例和迁移差分。满足以下条件后才允许进一步归档：

1. 新官方管道成为唯一产品入口；
2. 正式 SQL 正确率门禁通过；
3. 12 类函数全链路矩阵通过；
4. 新指标和新函数零核心代码扩展通过；
5. 长周期自动优化由正式编译器产生并达到门槛；
6. 调用图证明没有运行入口依赖待归档符号；
7. 完整测试、Doris 证据和回滚演练通过。

对于超大模块中的疑似无用函数，先使用静态搜索、覆盖率、运行调用和差分测试证明无引用，再在独立提交中删除。不能为了目录好看一次性移动核心代码。

## 6. 后续归档流程

1. 判断文件是当前规范、阶段记录、历史证据、生成产物还是缓存。
2. 把仍有效的结论合并到当前主线或对应正式文档。
3. 检查 README、项目索引、脚本、测试和 manifest 是否引用该路径。
4. 使用 Git 移入 `docs/history/` 或 `archive/`，不覆盖同名文件。
5. 更新本说明和历史区 README。
6. 运行文档链接检查、静态检查、完整测试和必要的 Doris 验证。
7. 在变更清单中记录原路径、新路径、原因和恢复方法。
