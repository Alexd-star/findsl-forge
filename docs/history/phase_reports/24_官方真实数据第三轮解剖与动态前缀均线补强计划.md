# 官方真实数据第三轮解剖与动态前缀均线补强计划

## 1. 当前判断

本轮拿到的官方真实资料已经可以确认，赛题组实际给出的数据不是完整金融数据库，而是三张 A 股行情相关表和一份 5799 条训练语料的 DSL Excel。三张表分别是股票代码表 `hsj_stock_code_info`、行情基本数据宽表 `hsj_stock_hq_basic`、行情衍生数据表 `hsj_stock_hq_ext`。这意味着项目必须把“能由三张表严谨落地的内容”做到尽量完整，同时对财务、基金、指数成分、用户持仓、公司画像等无字段来源的需求保持诚实，不能为了覆盖率生成伪 SQL。

截至本轮分析前，项目证据显示：官方样例共 5799 条，语法解析成功 5792 条，Doris SQL 编译成功 1718 条，编译失败 4074 条。失败原因中，`UNSUPPORTED_OFFICIAL_INDICATOR` 仍占最大头，为 3928 条；但其中多数并不是编译器偷懒，而是官方三表确实没有对应数据域。例如“成分股”“跟踪指数”“基金十大重仓股”需要指数/基金持仓表，“归母净利润”“净资产收益率”“分红金额”需要财务报表或分红表，“我的持仓股”需要用户账户表，“热门”“龙头股”“主营业务”需要公司画像或题材热度数据。这些内容在没有官方新增数据的阶段不能硬补。

真正值得继续开发的是另一类缺口：语义来自官方 DSL 规范，且底层三表已经提供了足够字段，只是当前编译器尚未把它们全部泛化。第三轮分析发现，动态 `N日均线`、`N日均量线` 就属于这一类。官方说明明确提到候选指标中存在可实例化占位符，例如 `X日均线` 可以被改写为 `10日均线`。官方训练语料中也确实出现了 `7日均线`、`11日均线`、`13日均线`、`25日均线`、`45日均线`、`240日均线`、`754日均线`、`850日均线`、`3日均量线`、`8日均量线`、`200日均量线` 等实际样例。当前项目只预先物化了 3、5、10、20、30、60、120、200、250 日均线，以及 5、10、20、30、60 日均量线，因此其他窗口会报未支持指标。

## 2. 官方数据支持度

动态日均线可以由官方行情基本表中的 `closePx` 推导。项目已经在 Doris 中构建了 `hsj_stock_hq_basic_prefix`，其中包含 `row_no`、`close_prefix`、`close_count_prefix`。对任意窗口 N，某日的 N 日均线可以表达为：

```sql
(p.close_prefix - COALESCE(p_prev.close_prefix, 0))
/ NULLIF(p.close_count_prefix - COALESCE(p_prev.close_count_prefix, 0), 0)
/ 10000.0
```

其中 `p_prev.row_no = p.row_no - N`。如果历史不足 N 天，现有固定窗口逻辑也是从起始日累计到当前日；这个行为和当前 `ma3/ma5/ma10/...` 的物化计算保持一致，不另造规则。

动态日均量线可以由 `volume_prefix` 与 `volume_count_prefix` 推导，表达为：

```sql
(p.volume_prefix - COALESCE(p_prev.volume_prefix, 0))
/ NULLIF(p.volume_count_prefix - COALESCE(p_prev.volume_count_prefix, 0), 0)
```

成交量本身不是价格单位，不需要再除以 10000。这个判断与当前技术表中的 `volume_avg_5/10/20/30/60` 一致。

需要特别说明的是，`5周均线`、`1月均线`、`周均线空头排列` 等不能简单套用日线前缀窗口。周线、月线需要交易日重采样、周期收盘、周期成交量和跨周期 K 线规则；官方三表给的是日频数据，没有给出周/月 K 线物化口径。本轮计划会继续把这些指标标记为未支持，而不是把“5周”错误地当作“5日”。

## 3. 根因拆解

当前编译器的指标映射以静态字典 `INDICATORS` 为中心。这个设计适合字段名固定的指标，例如“最新价”“成交量”“涨停”“主力净流入”。对于 `7日均线` 这类窗口参数写在指标名里的官方指标，静态字典就会变得笨重：要么预先加很多列，要么每出现一个窗口就手动补一个别名。官方真实语料已经证明窗口不是固定几个数字，最大甚至出现了 850 日均线，因此继续追加静态别名不是成熟方案。

更合理的方案是加一层统一的指标解析器。编译器收到指标名后，先查静态字典；静态字典不存在时，再判断它是否匹配 `N日均线` 或 `N日均量线`。如果匹配，就生成一个 `IndicatorMeta`，其 `expression` 是可别名重写的 Doris 标量子查询。这样普通筛选、排名、聚合、出现次数、`cross_above/cross_down`、`reset/close_together` 都仍然走原有通道，不需要每个函数各写一套动态均线逻辑。

## 4. 本轮开发目标

本轮优先完成四件事。

第一，新增动态日均线支持。`indicator('', '', '7日均线', '今天', '', '', '') > 10` 应该能编译，并且 SQL 中要明确引用 `newzl.hsj_stock_hq_basic_prefix`、`close_prefix`、`close_count_prefix` 和 `row_no - 7`。

第二，新增动态日均量线支持。`indicator('', '', '8日均量线', '今天', '', '', '') > 1000` 应该能编译，并且 SQL 中要明确引用 `volume_prefix`、`volume_count_prefix` 和 `row_no - 8`。

第三，让动态指标进入所有已有函数路径。官方真实样例中动态均线经常出现在 `reset`、`cross_above`、`cross_down`、`golden_cross`、排名和左右指标比较中。如果只让普通 `indicator` 能用，项目仍然会在核心样例里失败。

第四，刷新官方覆盖率、readiness 和提交证据。开发完成后必须重新生成 `reports/official_slot_coverage.json`、`reports/official_slot_coverage.md` 和 `submission_artifacts/evidence_summary.md`，用新的数字说明本轮补强实际带来了什么，不凭口头判断。

## 5. 暂不处理的内容

本轮不伪造财务类指标。比如“归母净利润”“净资产收益率”“营业收入同比增长率”“分红金额”都需要财报或分红数据，官方三表没有字段来源。

本轮不伪造基金与指数成分。比如“成分股”“跟踪指数”“基金十大重仓股”需要专门的指数成分表、基金持仓表或权重表。

本轮不把公司画像当作行业字段。比如“主营业务”“热门”“龙头股”“优质”“潜力”“估值”并不等同于 `hyBlkRefName`，不能为了覆盖率用行业名硬凑。

本轮不把周线、月线当作日线。周/月均线要有明确重采样口径后再做，否则答辩时很容易被追问穿。

## 6. 验收标准

代码层面，新增测试必须先失败再通过。目标测试包括动态 `7日均线`、动态 `8日均量线`、动态均线在 `reset` 和 `cross_above` 中的使用，以及 `5周均线` 继续未支持。

覆盖率层面，官方编译成功数应高于当前的 1718。由于很多样例是复合条件，动态均线修好后，部分样例可能继续暴露下一个无字段指标；因此不能只看“动态指标出现次数”，要以完整 workbook 重新编译后的 `compile_ok` 为准。

证据层面，`submission_readiness.ps1` 需要通过，`evidence_summary.md` 需要显示新的 Pytest 数量、官方覆盖率和 Git HEAD。若 Doris 环境没有重新跑官方真实数据实测，文档中仍需区分“官方真实 CSV 前缀加速比”和“合成/集群放大性能证据”，不能把两个数字混用。

## 6.1 本轮执行结果

本轮实际不只完成了动态前缀均线，还顺手补齐了两个由官方真实语料暴露出的三表可落地缺口：`rank(...)` 作为数值表达式参与四则运算，以及 A 股股票语境下的 `每手股数`、`是否T+0` 交易规则常量。完整刷新官方 workbook 后，编译成功数从本轮开始前的 1718 条提升到 1804 条，净增 86 条；语法解析仍为 5792/5799，说明本轮没有掩盖官方原始 DSL 中的 7 条语法/词法瑕疵。

动态均线补强后，`7日均线`、`11日均线`、`25日均线`、`45日均线`、`754日均线`、`8日均量线` 等窗口不再需要逐一建列，统一走 `hsj_stock_hq_basic_prefix`。`rank(...)` 表达式补强后，原先的 `UNSUPPORTED_OFFICIAL_FUNCTION: rank` 已从覆盖率错误码中消失；剩余 rank 相关问题主要变成 `then` 链路形态或缺字段指标。`每手股数` 与 `是否T+0` 则作为股票适配器规则常量处理，非股票标的仍按原有 `select_type` 约束保持不可落地。

## 7. 后续优先级

动态均线之后，`rank(...)` 在表达式中的支持已经完成。当前下一批最值得做的是 `then` 链路中出现括号组合排名条件的情况，以及 `rank(..., count_exp)` 与聚合函数同时出现的时间排名语义。前者是 DSL 形态规范化问题，后者需要时间桶排名特征或更复杂的窗口子查询。

再下一批是 `count_exp` 作为左右表达式共同出现的情况，例如左右两个指标都带 `CONS=每日` 或 `EXIST>0`。这类语义涉及同一时间窗口内逐日比较，最好增加专门的窗口比较编译器，避免现在把每个 count_exp 只能挂在单个比较外层的限制扩大成误判。

最后是排名区间，如 `rank(...) between '[5%,10%]'` 和 `rank(...) ~= 10`。这类语义可以转成排名号区间或近似范围，但百分位排名与绝对名次必须分清，需要先定义精确规则。
