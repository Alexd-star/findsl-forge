# 19 赛题 19 完成度与下一步规划

本文根据官方赛题 19“行情选股 DSL 到高性能 Doris SQL 的自动化编译系统”整理当前项目完成度。与普通说明文档不同，本文把要求拆成三种状态：`implemented` 表示已有代码、测试或证据支撑；`partial` 表示主干可用但仍有边界；`needs_evidence` 表示不能靠代码假装完成，必须等待官方数据、官方 DSL 规范或现场 Doris 环境补证据。

同一份结果可以用命令生成：

```powershell
$env:PYTHONPATH='src'
python -m findsl.cli topic-compliance --output reports/topic_19_compliance_plan.md --json
```

## 3. 已补强内容

本轮已经补上两项能立即提升赛题符合度的能力。第一项是模板函数扩展。`configs/functions.json` 新增 `ABS`，通过 `sql_template` 和 `reference_op` 让简单数值函数进入通用语义校验、SQL 生成和 reference 计算路径。对应测试是 `tests/test_template_functions.py`，它验证 `ABS(indicator("main_net_inflow"))` 能编译、能进入 explain，并能通过 SQL/reference 等价验证。

第二项是赛题完成度报告。`src/findsl/topic_compliance.py` 提供机器化的完成度分类，CLI 命令为 `topic-compliance`。这个命令把官方要求分成 `implemented`、`partial`、`needs_evidence`，并输出下一步计划。它解决的是文档维护风险：以后不再只靠人工描述判断项目是否满足赛题，而是可以把当前证据和待办项集中生成出来。

## 4. 下一步开发规划

第一优先级是把官方 DSL 规范拿到后做逐项函数清单。当前项目已经覆盖主要函数族，但官方题面只写“12 类领域函数”，没有在 TXT 中展开完整清单，所以不能凭猜测宣称全量闭环。拿到官方规范后，应建立 `data/samples/official_function_matrix.jsonl` 或同类文件，把每一类函数至少放入一个正例和一个负例。

第二优先级是继续增强函数模板协议。当前 `ABS` 证明了简单数值标量函数可以通过 `functions.json` 的 `sql_template` 和 `reference_op` 进入 SQL 生成和 reference 验证；后续复杂时序函数应扩展为窗口模板、布尔模板和聚合模板。只有做到这些，才能更有底气地回应“新函数 0 行核心代码改动”。

第三优先级是官方数据到位后重跑 Doris 证据。需要按官方问句生成 baseline/optimized SQL、行数一致性、P50/P95/平均耗时和 10s 达标表。没有官方数据时，只能把现有 5M Doris 证据作为长窗口核心路径证明，不能把它说成所有查询的统一性能结论。

第四优先级是提交包格式。按参赛指南补齐精益画布、原创性声明、文件夹 `readme.txt`、统一模板 PPT 和 1 分钟视频，保证可运行测试之外的材料不丢分。
