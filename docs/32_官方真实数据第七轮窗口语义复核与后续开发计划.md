# 官方真实数据第七轮窗口语义复核与后续开发计划

生成时间：2026-06-10

## 1. 本轮判断的出发点

本轮工作的前提已经发生变化：目前比赛阶段可使用的“官方真实数据”已经明确，不再是假设以后还会补齐财务、基金、账户、指数成分或分钟级行情数据。当前官方资料目录只包含 DSL 规范、5,799 条官方槽位实例、一份 Doris 建表说明，以及三张 A 股日频行情相关 CSV。因此，项目后续开发必须围绕一个原则展开：能由官方三张表或项目从三张表确定性构建出的特征表支撑的能力，要尽量做到正确、稳定、高性能；没有真实字段来源的数据域，必须继续返回结构化不支持诊断，不能为了提高表面覆盖率而生成伪 SQL。

这个原则对比赛很重要。评委真正会追问的不是“为什么还有样例不能编译”，而是“你生成的 SQL 是否和官方数据一致、是否能在 Doris 上执行、是否知道哪些意图没有数据来源”。项目现在的优势也在这里：它把可落地样例和不可落地样例分开统计，能够解释每一类失败原因，避免把财务、基金、账户等缺表问题伪装成普通行情字段过滤。

## 2. 官方真实数据再解读

本轮重新核对官方资料后，当前真实资料可以分成两组。

第一组是 DSL 资料。`选股 DSL 规范文档/选股提槽说明.txt` 给出了候选函数、槽位含义和表达约束，核心函数包括 `indicator`、`rank`、`belong_industry`、`queryData`、`cross_above`、`cross_down`、`close_together`、`reset`、`golden_cross`、`record_high`、`record_low`、`position`。其中 `count_exp` 被定义为 `CONS/EXIST + 逻辑符号 + 次数 + 单位`，单位主要是年、季度、月、周、日。这个定义说明“连续出现”和“出现次数”是官方 DSL 的核心难点之一，但也说明分钟级连续、闭区间次数、无指标排名等表达如果没有进一步说明，不能随意猜口径。

第二组是 Doris A 股行情数据。`hsj_stock_code_info` 是股票代码与静态属性表，包含市场号、股票名称、行业块引用、ST 标识、沪股通/深股通/陆股通、创业板、科创板等字段。`hsj_stock_hq_basic` 是行情基础宽表，覆盖日频价格、成交量、成交额、内外盘、委买委卖、总股本、流通股本、市值、市净率、市盈率、涨跌停、压力位、支撑位、影线、涨跌幅、成交均价等字段。`hsj_stock_hq_ext` 是行情衍生表，包含三/五/十分钟涨速、集合竞价、主力资金、大单/中单/小单资金、筹码形态、最大回撤、MA 角度、创 N 日新高/新低、连涨连跌、破板次数等字段。

这三张表能够支撑“日频行情选股 DSL 到 Doris SQL”的主干能力，例如价格、涨跌幅、成交量、成交额、换手率、量比、资金流、集合竞价、涨跌停、行业过滤、市场过滤、排名、时间窗口、连续/出现次数、长周期均线、创新高/新低、行业聚合和部分技术形态。它们不能支撑财务报表、主营业务文本、基金产品、基金持仓、指数成分权重、用户持仓/自选股、龙虎榜、股权质押、控股股东、分钟级 K 线序列、MACD/BOLL/RSI 原始指标等数据域。后者在官方 workbook 中占比较高，因此剩余未编译样例主要是数据包边界，而不是编译器主链路缺失。

## 4. 本轮发现的关键语义问题

本轮深度复核时发现一个很细但很关键的问题：`cross_above`、`cross_down`、`golden_cross` 这类穿越事件不能只在目标日期窗口内部计算 `LAG()`。

举例来说，如果用户问“近 5 日上穿 60 日均线”，统计窗口是 2026-04-10 到 2026-04-14。判断 2026-04-10 当天是否发生上穿，需要比较 2026-04-10 的左右指标和 2026-04-09 的左右指标。如果 SQL 的内层事件子查询直接写成 `wb.bizdate BETWEEN '2026-04-10' AND '2026-04-14'`，那么窗口函数 `LAG()` 在 2026-04-10 这一行看不到 2026-04-09，首日事件会被漏判。这种错误不一定影响编译数量，但会影响语义正确性，是答辩和真实评测里更危险的问题。

正确做法是把“取上一交易日所需的源数据窗口”和“统计事件次数的目标窗口”拆开。源数据层只限制股票关联和日期上界，例如 `wb.bizdate <= '2026-04-14'`，让 `LAG()` 能看到目标窗口之前的历史行。事件统计层再使用 `event_rows.bizdate BETWEEN '2026-04-10' AND '2026-04-14'`，保证窗口外事件不会被算入 `CONS/EXIST`。这相当于把穿越判断拆成两步：先在足够长的历史序列中判断每日是否穿越，再只统计目标窗口内发生了几次。

## 5. 本轮已执行的开发

本轮按 TDD 处理该问题。先在 `tests/test_official_slot.py` 中写入红测，分别覆盖：

1. `cross_above('', '', '最新价', '60日均线', '近5日', '', 'CONS=每日') = True` 必须把事件窗口写成 `event_rows.bizdate BETWEEN '2026-04-10' AND '2026-04-14'`。
2. `cross_above(..., 'EXIST=1日')` 的事件源必须保留 `wb.bizdate <= '2026-04-14'`，不能把下界放到 `wb` 源表上。
3. `golden_cross('', '', '5日均量线', '10日均量线', '近10个交易日', '', 'EXIST=2日') = True` 在交易日历约束下必须统计 `event_rows.bizdate BETWEEN '2026-04-01' AND '2026-04-14'`。

红测失败后，在 `src/findsl/official_slot.py` 中新增 `_lag_event_window_where()`，专门把日期槽归一化结果拆成两类条件。对于精确日期，源层生成 `source_alias.bizdate <= end_date`，事件层生成 `event_alias.bizdate = end_date`。对于日期区间，源层只取区间结束日上界，事件层保留完整区间。对于空日期或运行时无法归一化的日期，继续保持既有保守行为，不额外伪造窗口。

修复后的穿越事件 SQL 形态如下：

```sql
FROM (
  SELECT wb.bizdate AS bizdate,
         (<left_today> > <right_today>
          AND LAG(<left_today>) OVER (PARTITION BY wb.mktcode, wb.tgtcode ORDER BY wb.bizdate)
              <= LAG(<right_today>) OVER (PARTITION BY wb.mktcode, wb.tgtcode ORDER BY wb.bizdate)) AS event_value
  FROM newzl.hsj_stock_hq_basic AS wb
  LEFT JOIN ...
  WHERE wb.mktcode = base.mktcode
    AND wb.tgtcode = base.tgtcode
    AND wb.bizdate <= '2026-04-14'
) AS event_rows
WHERE event_rows.bizdate BETWEEN '2026-04-10' AND '2026-04-14'
```

这个改动没有扩大支持口径，但提高了已支持穿越事件的正确性。换句话说，覆盖数字不变是正常的；真正改善的是“已编译 SQL 是否严格符合金融时间序列语义”。

## 7. 剩余待做项目

后续最值得继续投入的是“仍能基于官方三表真实落地”的小范围语义，而不是盲目扩展缺数据域。

第一优先级是表达式级聚合 `count_exp`。官方样例里存在 `indicator(..., AVG, count_exp) / indicator(...) < ...` 这类结构。它本质上不是普通指标比较，而是要先在时间窗口内对左侧指标做聚合，再把聚合值和右侧指标或常数进行比较，最后统计满足条件的天数或桶数。这一类仍然可能由 `hsj_stock_hq_basic` 或 `hsj_stock_hq_ext` 支撑，值得继续设计。实施时必须限制在同一 market/filter/date/select/count_exp scope 内，避免把不同窗口的聚合值硬拼在一起。

第二优先级是日期表达的精确归一化。已经支持的表达包括年、年月、月日、近 N 日、近 N 月、本月、本季度、复合前后偏移等。后续可以继续从覆盖报告中提取 warning 样例，优先补“有明确边界”的表达。对于“近期”“前期”“尾盘”“收盘后”这类缺少明确日频边界或涉及盘中阶段的词，不应强行归一成固定天数。

第三优先级是 Doris 执行证据的再刷新。只要 SQL 形态发生变化，尤其是窗口函数、CTE、聚合或特征表相关变化，就应重新执行官方 Doris evidence 脚本，确认 SQL 可以在真实 Doris 环境中解释和执行，并且行数、EXPLAIN、基线/优化对比没有漂移。

## 8. 暂不建议做的方向

以下方向不建议继续投入代码实现，除非赛题组补充对应真实数据：

1. 财务报表类指标：归母净利润、营业收入、净资产收益率、股息率、分红金额、研发费用等。
2. 基金和指数关系：基金十大重仓股、跟踪指数、成分股、投资市场、基金规模、基金类型等。
3. 用户账户数据：我的持仓股、我的自选股、账户利润、个人拥有比例等。
4. 公司画像和文本相似：主营业务、热门、潜力、优质、龙头股、业务相似等。
5. 分钟级序列：`CONS=10分钟`、尾盘未封板等需要分钟 K 线或盘中事件序列的意图。
6. 未定义次数区间：`EXIST=2-5`、`CONS=1-2月`、`CONS=30日-60日`。如果没有官方进一步定义，直接实现会存在“连续长度范围”和“出现次数范围”混淆。

保留这些不支持诊断不是保守，而是对真实数据负责。比赛答辩时可以明确说明：系统的目标不是把所有自然语言都伪装成 SQL，而是把有数据依据的选股 DSL 稳定、可审计、高性能地编译为 Doris SQL。

## 9. 下一步执行顺序

后续建议按下面顺序推进：

1. 对表达式级聚合 `count_exp` 写最小红测，优先选取官方 workbook 中仍属于行情三表可解释的样例。
2. 设计只支持单一 scope 的聚合表达式子查询，不处理混合日期、混合市场、混合 count_exp 的复杂情况。
3. 实现后跑 `tests/test_official_slot.py`，再跑全量 pytest。
4. 刷新 `reports/official_slot_coverage.json` 和 `reports/official_slot_coverage.md`。
5. 如果覆盖数下降或 warning 减少，同步更新 README、CHANGELOG 和本系列文档。
6. 运行 `scripts/submission_readiness.ps1`，确认 required gates 仍通过。
7. 如 Doris SQL 形态发生明显变化，重新运行官方 Doris evidence，并把 evidence 快照纳入提交包。

这一路线的目标不是追求无限功能膨胀，而是把当前官方数据包可证明的能力做到顶尖：语义不漂、SQL 不伪造、性能有证据、失败能解释、测试可回归、Git 可回溯。
