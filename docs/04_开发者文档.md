# 04 开发者文档

本文面向继续开发 FinDSL Forge 的工程人员。任务顺序以 [00_当前开发主线.md](00_当前开发主线.md) 为准；正式官方代码位于 `src/findsl/official/`，旧手写编译器只作兼容和回归。

## 1. 开发原则

1. 确定性核心优先。LLM 只能产生 DSL 候选，不能绕过 ANTLR、类型、IR、SQL validator 和独立 oracle。
2. 能力族优先。先按解析、类型、语义、关系、物理、数据或非法输入定位根因，再实现通用规则；禁止按完整 DSL 或 Excel 行号打补丁。
3. 依赖单向。兼容层可以调用新核心，新核心不得依赖 `official_slot.py`、`compiler.py`、`parser.py`、`semantic.py` 或 `sqlgen.py`。
4. 配置可审计。指标、函数、政策和外部范围必须经过 Schema、版本、哈希和来源校验，配置不能注入任意 SQL。
5. 等价优先。优化规则必须保持完整结果一致；性能选择和等价变换分开实现。
6. 证据闭环。实现、测试、真实 Doris、metadata 和文档必须对应同一 HEAD、配置和数据快照。

## 2. 处理一个缺口

1. 用 `official_gap_analysis.py` 确认所属能力簇和影响行数。
2. 在 frontend、semantics、domain、IR、optimizer、physical、backend 或 external Provider 中确定唯一责任层。
3. 先补最小失败测试和同簇批量回归，不添加行号/原文特判。
4. 实现通用规则，并检查 Typed AST、Logical IR 和 Physical IR 是否保持职责边界。
5. 运行 SQL/reference 或独立 Doris reference 完整结果比较。
6. 运行受影响测试、Ruff、import-linter 和全量 pytest。
7. 若指标改变，刷新 current evidence；历史结果保留但不进入当前汇总。

## 3. 新增指标

普通已有数据域指标优先增加官方指标目录配置、列类型、资源绑定和测试数据。若指标来自新表，还要增加 Physical Catalog、Doris schema、Provider/导入流程和数据快照。完成标准不仅是 SQL 能生成，还包括列真实存在、非空执行、独立结果一致和核心源码树在盲扩展前后哈希相同。

早期 `configs/indicators.json` 仍服务内部 FinDSL；正式零代码指标证据必须来自官方 ANTLR/IR/SQLGlot 主链路。

## 4. 新增函数

先判断函数能否由已有受控代数组合：

- 标量函数：类型签名 + 受控表达式模板 + reference operation；
- 聚合/窗口函数：窗口模板 + 空值/除零政策 + Physical Strategy；
- 事件函数：状态/时序模板 + 时间政策 + 参考解释；
- 新关系语义：只有现有 IR 无法表达时才新增节点和 lowering。

“零核心代码”只适用于模板协议已覆盖的语义，不能解释为 JSON 可以发明任意未知算法。配置模板必须是白名单代数，不接受可执行 SQL 字符串。

## 5. 修改规划或 Doris SQL

优先查看：

```text
src/findsl/official/ir/
src/findsl/official/optimizer/
src/findsl/official/physical/
src/findsl/official/backend/
tests/official/
```

逻辑规则变更要验证等价、幂等和规则顺序；物理候选变更要保存成本分量、选择理由、回退策略和 Doris Profile；renderer 变更要通过 SQLGlot 方言往返与安全校验。不要在 backend 临时修补本应由语义或 IR 表达的问题。

## 6. 质量门禁

```powershell
$env:PYTHONPATH = "src"
python scripts/generate_antlr.py --check
python -m ruff check .
lint-imports
python -m pytest
python -m findsl.cli official-suite --json
```

当前工作区全量测试为 `1042 passed`，仅代表已有断言通过；正式正确率仍需独立真值集。提交前再运行 readiness、Doris 证据、文档链接和 metadata 一致性检查。

## 7. 代码审查重点

- 是否在正确层解决根因，而不是把问题推到 renderer；
- 是否出现 DSL 原文、Excel 行号或单个证券名称特判；
- 是否让正式核心重新依赖旧管道；
- 是否用 current membership 回答历史成员查询；
- 是否把迁移率、编译率或空结果写成正确率；
- 是否把模型估算扫描量写成 Doris 实测；
- 是否保证稳定排序、NULL、除零、窗口预热和时间政策；
- 是否提供失败诊断、回退策略、测试和真实证据。

## 8. 提交方式

一次提交围绕一个能力或整理主题。代码和测试先提交，真实证据在 clean HEAD 上生成后单独提交，便于确认 evidence 指向的版本。提交前检查 `git diff --check`、全量门禁和文档链接；不混入无关格式化、缓存或大文件。
