# 严格官方编译基线与口径说明

## 1. 文档用途

本说明用于统一官方槽位 DSL 的解析、编译和覆盖率口径。代码、报告、截图、答辩稿和 metadata 引用官方工作簿指标时，应以本文定义为准。

过去的覆盖率报告把“经过容错后能够生成一段 SQL”记为 `compile_ok`。这个数字适合观察适配器覆盖范围，却不能证明原始 DSL 无语法瑕疵，也不能证明生成结果没有 warning、恒真条件或恒假条件。新编译基线将 strict 与 recovery 分开统计，不再把两类结果混在一起。

## 2. 两种编译模式

### 2.1 strict 模式

strict 模式直接解析原始 DSL，不静默删除前导布尔运算符、边界引号或多余右括号。函数参数必须与官方签名完全一致，所有槽位参数必须是字符串字面量。AST 通过类型检查后才能进入 SQL 生成。

只要出现下列任一情况，strict 编译就失败：

1. 原始 DSL 需要源码修复；
2. 编译过程产生 warning；
3. 数据域缺失，需要用 `1=0` 表示无可验证结果；
4. 日期无法落到确定区间，需要用 `1=1` 保留运行时语义；
5. 函数 arity、槽位类型、算术类型或比较类型不合法；
6. 指标不在官方三表及已实现派生特征的可落地范围内。

对可修复但原始 strict parse 失败的输入，strict compiler 会运行一次 recovery 诊断探测。探测只用于列出 repair code 和恢复 AST 的语义错误，不会把恢复 AST 交给 SQL 生成。

### 2.2 recovery 模式

recovery 模式用于训练语料审计、问题定位和兼容迁移。它会记录源码修复，并尽可能继续解析和编译。返回结果中的 `repairs`、`warnings`、`fallback_predicates`、`degraded` 和 `strict_success` 必须一并保留。

recovery 编译成功只说明编译器返回了结果对象。若 `strict_success` 为 `false`，该结果不能计入严格成功率，也不能在答辩中称为“完全正确编译”。

## 3. 官方工作簿实测结果

测试对象为官方 `选股提槽实例.xlsx` 的“训练语料”工作表，共 5,799 条。

| 指标 | 当前结果 | 含义 |
|---|---:|---|
| strict parse 成功 | 5,792 | 原始 DSL 不需要修复即可建立 AST |
| strict parse 失败 | 7 | 原始文本存在可定位的标点或前导运算符问题 |
| recovery parse 成功 | 5,799 | 7 条问题语料经结构化修复后均可解析 |
| 发生源码修复 | 7 | repair 记录带原始源码坐标 |
| strict compile 成功 | 1,097 | 原始语法、函数签名、类型、数据映射和降级门禁均通过 |
| recovery compile 成功 | 1,830 | 容错后可以返回 SQL 结果，不等同于 strict 成功 |
| 含 warning 的 recovery 结果 | 731 | 存在近似语义、缺失数据域或日期运行时归一化 |
| degraded recovery 结果 | 733 | repairs、warnings 或结构化 fallback 至少出现一项 |
| `1=0` 降级谓词 | 472 | 官方三表无法提供目标市场、标的类型或日期区间 |
| `1=1` 降级谓词 | 328 | 日期槽无法静态归一到确定区间 |

strict 全量编译率为 18.92%，recovery 全量编译率为 31.56%。这两个比例共同反映语料合法性、函数与类型检查、降级门禁以及官方三表适配边界，不是自然语言理解准确率，也不是 SQL 执行结果正确率。

### 3.1 七条源码修复

当前 repair 分布如下：

| repair code | 条数 | 处理内容 |
|---|---:|---|
| `DANGLING_EDGE_QUOTE` | 4 | 删除包裹完整表达式、且可确定为文档噪声的孤立边界引号 |
| `ORPHAN_LITERAL_QUOTED` | 1 | 为槽位中的孤立日期字面量补齐引号 |
| `UNMATCHED_CLOSING_PAREN` | 1 | 删除无法与左括号匹配的右括号 |
| `LEADING_BOOLEAN_OPERATOR` | 1 | 删除表达式开头多出的 `and/or/then` |

repair 的 `position` 使用原始 DSL 坐标。组合修复和同类多次修复分别记录，不再用修改后文本的偏移量冒充原文位置。

### 3.2 strict 编译失败分布

| 错误码 | 条数 | 说明 |
|---|---:|---|
| `UNSUPPORTED_OFFICIAL_INDICATOR` | 3,869 | 指标需要财务、基金、指数成分、账户持仓、龙虎榜或其他未提供数据域 |
| `OFFICIAL_DEGRADED_SEMANTICS` | 737 | 需要 repair、warning 或 fallback，strict 模式拒绝 |
| `OFFICIAL_TYPE_ERROR` | 92 | 算术、比较、裸标识符或 `between` 类型不合法 |
| `UNSUPPORTED_OFFICIAL_COUNT_EXP` | 3 | 当前三表不足以可靠实现相应次数/连续语义 |
| `UNSUPPORTED_OFFICIAL_PERIOD_FUNCTION` | 1 | 周期函数缺少可验证的数据或算法定义 |

strict compiler 会把官方 7 条可修复语料归入 `OFFICIAL_DEGRADED_SEMANTICS`，因此 strict compile 错误分布中不再出现孤立的 `OFFICIAL_LEX_ERROR` 或 `OFFICIAL_PARSE_ERROR`。

## 4. 历史指标如何解释

2026-07-06 的历史报告记录 `parse_ok=5,799`、`compile_ok=1,882`。这两个字段当时都使用 recovery 口径，其中 `compile_ok` 的定义是“未抛异常并返回 SQL”。它不能证明以下事项：

- 原始 DSL 能通过 strict parse；
- 函数参数数量与官方签名完全一致；
- 所有槽位都是字符串字面量；
- 数值指标没有与普通文本比较；
- SQL 不含 `1=0` 或 `1=1` 降级条件；
- SQL 已在 Doris 中执行并与独立判定基准（test oracle）等价。

引入精确函数签名和类型分析后，recovery compile 从 1,882 调整为 1,830。减少的 52 条主要是过去被参数切片或字符串强制转换静默接受的非法调用。该变化修正了错误口径，不能描述为覆盖能力下降。

为兼容旧脚本，覆盖率 JSON 暂时保留 `parse_ok` 和 `compile_ok`。它们分别映射到 `recovery_parse_ok` 和 `recovery_compile_ok`。新文档和截图不得只展示这两个旧字段。

## 5. 函数签名和类型门禁

官方 12 类函数已在 `src/findsl/official/signatures.py` 中登记精确槽位顺序。`indicator` 为 7 槽，`rank` 为 8 槽，`belong_industry/queryData` 为 5 槽，交叉与技术事件函数为 7 槽，`record_high/record_low/position` 为 8 槽。

语义分析器位于 `src/findsl/official/semantics.py`。主要规则如下：

- 函数参数数量必须精确相等，不能忽略额外参数；
- 槽位只接受字符串 `OfficialLiteral`，数字、布尔值和表达式不能自动转成字符串；
- `indicator/queryData/belong_industry` 通过完整指标 resolver 推导 numeric、boolean、string 或 time；
- 百分比字面量按 numeric 处理，时间文本按 time 处理；
- 四则运算只接受 numeric；
- 有序比较只接受同型 numeric 或 time；
- `~=` 只允许 numeric 或 string，禁止用于 boolean；
- `between` 右侧必须是显式区间；
- 裸标识符不能绕过类型检查；
- 未映射指标继续进入 grounded-data 诊断，不伪装成类型错误。

## 6. fallback 的记录方式

编译器不再扫描最终 SQL 文本来猜测是否出现 fallback。SQL 中合法的 `WHERE 1=1` 占位条件，或字符串值 `'1=0'`，都不应被误判。

日期归一化、市场缺失和标的类型缺失会显式写入 `fallback_predicates`。当前值域为 `1=0` 和 `1=1`。覆盖率报告直接统计该结构化字段。

## 7. 复现命令

运行聚焦测试：

```powershell
python -m pytest tests\test_official_semantics.py tests\test_official_slot.py tests\test_cli.py -q
```

运行项目全量测试：

```powershell
python -m pytest -q
```

生成双口径覆盖率证据：

```powershell
$env:PYTHONPATH='src'
python -m findsl.cli official-slot-coverage `
  --workbook '<官方目录>\选股 DSL 规范文档\选股提槽实例.xlsx' `
  --mode recovery `
  --json-output reports\phase1_official_coverage.json `
  --report-output reports\phase1_official_coverage.md
```

检查单条 strict 编译：

```powershell
$env:PYTHONPATH='src'
python -m findsl.cli official-slot-compile `
  "indicator('沪', '', '成交量', '2026-04-14', '', '', '') > 1000" `
  --mode strict --json
```

strict 拒绝是预期的受控失败路径。使用者需要根据 `error.code` 区分数据边界、降级语义和非法输入。带 `--json` 时，CLI 返回稳定的 `error.code/error.message`，进程退出码为 2，不输出 Python traceback。

## 8. 这些指标能证明什么

当前证据可以证明：

- 官方 5,799 条 DSL 都可在 recovery 模式建立 AST；
- 5,792 条原始 DSL 不需要源码修复；
- 12 类官方函数执行精确 arity 和字符串槽位检查；
- strict 与 recovery 结果、错误码和样本分别统计；
- fallback 来自结构化编译诊断，不靠 SQL 文本搜索；
- 覆盖率报告可以复现，并能追溯到具体 Excel 行。

当前证据不能单独证明：

- 1,097 条 strict SQL 在 Doris 上全部执行成功；
- 每条 SQL 与自然语言问题完全等价；
- 未提供的数据域可以通过算法推断得到；
- 当前三表适配范围等于赛题完整业务范围；
- 单机 Docker Doris 性能等于生产集群性能。

这些结论需要 Doris 实际执行、独立判定基准、逐问句结果核验和 Profile 证据共同支持。

## 10. 后续引用规则

1. 报告正文同时列出 strict 和 recovery，不只写 `compile_ok`；
2. “编译成功率”必须注明模式和分母；
3. recovery 结果若 `strict_success` 为 `false`，统一称为“容错编译结果”或“降级结果”；
4. `1=0/1=1` 数量引用 `fallback_predicates` 统计，不扫描 SQL 文件；
5. 截图必须包含报告生成命令、官方工作簿路径、Git HEAD 和生成时间；
6. 后续 ANTLR 前端、Typed AST/IR 和 Doris 执行证据更新后，应重新生成本报告，不手工改数字。
