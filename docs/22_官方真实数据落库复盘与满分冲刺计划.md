# 22 官方真实数据落库复盘与满分冲刺计划

本文档记录 2026-06-10 拿到官方赛题组真实数据后的再次分析、工程修复、Doris 落库证据和后续冲刺路线。它的写法尽量贴近真实验收材料：哪些已经由真实数据证明，哪些只是当前数据包没有覆盖，哪些需要继续优化，均明确区分，避免把小样本、合成数据或旧证据混作官方证据。

## 22.1 当前结论

项目已经从“赛题原型”推进到“官方真实数据可复现执行”的阶段。官方三张 CSV 已经完整导入本地 Apache Doris，基础表行数与官方 CSV 完全一致：股票代码表 `5686` 行，行情基础宽表 `13650347` 行，行情衍生表 `6170822` 行。由行情基础表派生出的 `hsj_stock_hq_basic_prefix`、`hsj_stock_hq_ext_prefix`、`hsj_stock_hq_basic_technical` 三张特征表也都达到 `13650347` 行。换句话说，当前系统不再停留在“能生成 SQL”，而是已经在真实 Doris 环境里完成了全量落库、特征构建、行数核验和查询证据采集。

官方 workbook 覆盖率保持稳定：共 `5799` 条样例，`5792` 条可解析，`1682` 条可以编译成基于官方三表或确定性派生特征表的 Doris SQL。剩余失败主要不是编译器随意漏做，而是官方当前数据包没有提供财务报表、基金持仓、指数成分、用户持仓、龙虎榜、主营业务、题材热度等数据域。项目现在采用严格口径：没有数据来源的指标不生成伪 SQL，只输出可解释的缺失数据域诊断。

当前最重要的工程突破是解决了真实数据落库和特征构建中的三个硬问题：官方 CSV 中 `lastPx/preClosePx` 存在大量空值，schema 已改为可空；Doris Stream Load 在 Windows Docker Desktop 下经 FE 重定向会不稳定，脚本改为带 `Expect: 100-continue` 直连 BE `8040`；长窗口技术特征表单次大 INSERT 会触发单 BE 内存限制，已经改成 `mktcode + tgtcode hash bucket` 双层分片构建，16 桶下最大单批约 49.4 万行，最终 48 个分片全部执行完成。

## 22.2 官方真实数据解读

官方数据目录包含两个核心部分：`选股 DSL 规范文档` 和 `Doris A股行情数据集`。前者给出 DSL 语法说明和 `选股提槽实例.xlsx`，后者给出可以真正导入 Doris 的三张 A 股行情 CSV。当前比赛阶段没有更多数据，因此项目必须以这三张表为数据边界，不能为了提高覆盖率臆造外部字段。

`hsj_stock_code_info.csv` 是证券代码与标志信息表。它提供 `mktcode`、`tgtcode`、`name`、`tztcode`、ST 标志、沪深京 A 股标志、沪股通/深股通/港股通相关标志、科创板/创业板标志和行业字段。它可以支撑市场过滤、行业/板块名称匹配、股票名称展示和部分布尔类筛选。

`hsj_stock_hq_basic.csv` 是行情基础宽表，也是项目 SQL 的主表。它包含 2006-01-04 至 2026-04-14 的 A 股行情，字段覆盖开高低收、成交量、成交额、换手率、量比、估值、涨跌停、支撑压力、股本等。价格和比例类字段以整数缩放存储，编译器输出 SQL 时按 `10000.0` 转换为人类可读单位。

`hsj_stock_hq_ext.csv` 是行情衍生表，日期范围为 2018-08-20 至 2026-04-14。它提供涨速、集合竞价、主力资金流、大小单、筹码、创新高低天数、连涨连跌、破板次数等字段。由于它的历史范围晚于基础宽表，SQL 采用 `LEFT JOIN`，避免把缺失衍生数据误判为股票不存在。

## 22.4 本轮根因排查与修复

第一个根因是 schema 与真实 CSV 空值不一致。早期设计把 `lastPx` 和 `preClosePx` 当作必填字段，但真实 `hsj_stock_hq_basic.csv` 中 `lastPx` 为空 10735953 行，`preClosePx` 为空 28507 行。强行 `NOT NULL` 会造成 Stream Load 失败或行过滤。当前 schema 已把这两个字段设为可空，并保留其他确认为非空的主键和复权因子字段。

第二个根因是 Stream Load HTTP 链路。Doris Stream Load 官方流程是客户端向 FE 发起请求，再由 FE 重定向到 BE；也可以直接指定 BE 作为 Coordinator。Windows Docker Desktop 下，FE 重定向后的容器内网地址可能不是宿主机可访问地址。本项目脚本因此默认直连 `127.0.0.1:8040`，并显式传入 `Expect: 100-continue`、`strict_mode:false`、`max_filter_ratio:0`、`timeout:7200`。这样既允许真实空数值落为 `NULL`，又要求过滤行数为 0。

第三个根因是单次技术特征构建过大。`hsj_stock_hq_basic_technical` 要计算 MA3/5/10/20/30/60/120/200/250、均量线、K 线形态、放量、均线排列和支撑压力穿越。如果一次性对 1365 万行做多次 prefix self join，在单 BE Docker 环境下会触发 Load tracker 5GB 内存限制。当前修复不是调大内存“赌过去”，而是把任务拆成 3 个 `mktcode` 乘以 16 个 `tgtcode` hash bucket。每个 INSERT 的数据量可控，失败时也能定位到具体分片。

第四个根因是旧性能证据的对比口径不严谨。原 baseline 为了减少计算量，把窗口限制在最近 80 个自然日内，这对停牌或稀疏交易股票不等价。现在 baseline 改为完整历史窗口，prefix 查询使用预计算字段，并在报告生成前强制检查两者行数一致。如果 baseline/prefix 行数不一致，脚本直接失败，不允许输出误导性加速报告。

## 22.6 仍需补强的内容

第一，`reset` 和 `close_together` 仍需要可解释阈值。官方 DSL 高频出现“回调”“粘合”等形态，但官方并没有给出统一阈值。如果硬编码一个比例，答辩容易被问穿。下一步应把阈值写入 `configs/official_technical_patterns.json`，例如均线粘合用 `max(ma5,ma10,ma20)-min(...)` 与收盘价的比例衡量，回调用最近高点到当前价的跌幅区间衡量，并在文档说明默认参数可以调。

第二，rank 特征表还可以继续做。当前 rank 可以生成 Doris SQL，但对于 `rank(..., count_exp)` 或链式 rank + 时间桶统计，现场窗口仍会偏重。建议新增 `hsj_stock_rank_feature_daily/weekly/monthly`，预计算常用指标的日/周/月排名，字段包括 `bucket_key`、`indicator_name`、`direction`、`rank_no`。这样能把高频排名样例从窗口排序转成查表过滤。

第三，物理表设计可以进一步比赛化。当前官方表遵循原始 `UNIQUE KEY(mktcode,tgtcode,bizdate)`，利于股票维度唯一性，但大量 DSL 以日期为主过滤。后续可新增 date-leading 派生表或物化视图，例如 `*_by_date`，让 `bizdate` 成为排序前缀，以提升按日/按区间筛选的稳定延迟。该优化要以新 evidence 证明，不应只写在 PPT。

第四，缺失数据域要做成答辩亮点，而不是遮掩短板。当前官方三表没有财务、基金、指数成分、用户持仓、龙虎榜等数据。项目应把这些样例归为“需要外部数据域”，并说明一旦接入相应表，只需在 registry、schema、指标映射和测试中扩展，不需要改写编译器主链路。

第五，提交快照要更新。`reports/` 是本地运行产物，默认不提交。最终交付必须把 `official_doris_evidence.md/json`、`official_slot_coverage.md/json` 复制到 `submission_artifacts/evidence_snapshots/`，并更新 `evidence_metadata.json`、`evidence_summary.md`、README、交付说明和答辩材料中的数字。

## 22.9 技术依据

Apache Doris 官方文档说明，Stream Load 通过 HTTP 同步导入本地文件，可以由 FE 重定向到 BE，也可以直接指定 BE 作为 Coordinator；示例命令中包含 `Expect:100-continue`，并且返回总行数、加载行数和过滤行数，适合本项目做行数验收。Doris 官方资料还说明 Unique Key 模型适合主键唯一场景，Merge-on-Write 对读路径更友好；窗口函数和 `ROW_NUMBER()` 是排名、移动平均、滚动统计等分析任务的基础。本项目的 Doris SQL 设计和证据采集均围绕这些能力展开。
