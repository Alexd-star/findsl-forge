# 开发路线

## 1. 当前判断

主架构方向正确，不需要推倒重来。当前低效感主要来自早期以阶段文件和单句缺口推动开发，造成文档、证据和兼容代码同时增长。后续必须以“通用能力族 + 可量化退出条件”为单位推进，正式编译链保持单一主线，最终展示材料等功能封板后再制作。

## 2. 已完成的封板工作

### P0：评分硬门禁

1. **正式编译延迟基准已建立。** 48 条分层语句覆盖 12 类函数、复合布尔、多阶段排名和主要计划族，记录各阶段 P50/P95/P99；门禁直接读取机器 JSON，不再使用 10 条轻量样例代表正式 P95。
2. **配置式新函数盲测已完成。** 安全表达式树支持算术、比较、布尔、空值保护和嵌套组合；任意 SQL、类型不匹配、越界参数和过深模板均拒绝。`relative_gap` 不增加核心函数分支，并通过真实 Doris 独立结果集验证。
3. **正式正确率集已扩至 240 条。** 保留 127 条历史人工 reference、30 条平衡组合，新增交集、并集、嵌套优先级和配置函数用例。每条比较完整结果哈希，空集也作为有效语义结果参与比较。
4. **长周期证据已由单例扩成五类矩阵。** 成交量 SUM/AVG、成交额 SUM、收盘价 SUM/AVG 均在官方长周期数据上比较基线和前缀计划，最低加速 `11.947x`、中位 `13.688x`，完整结果哈希一致。
5. **正式执行矩阵已重采。** 48 条查询全部与 reference 一致且 P95 `<10s`，当前最大 P95 `2802.085ms`。
6. **编译解释和规则目录已收口。** `FINDSL EXPLAIN` 固定展示六阶段产物，显式比较 `RAW / PARTITION / MV / PREFIX`；`FinancialRuleCatalog` 和优化规则契约均进入可审计编译路径。
7. **能力矩阵和 Hero Query 已建立。** 12 类函数各层覆盖由 240 条正式基准自动生成；Hero Query 一次覆盖 `CONS + EXIST + then + rank + 区间 + 市场集合交`，并在真实 Doris 与独立 SQL 完整哈希一致。

### P1：完整性与泛化

1. 12 类函数均进入 Grammar、Typed AST、Logical IR、Physical IR、SQL 与 reference case 路径，正确率基准自动检查函数覆盖和每类最低样本数。
2. 对剩余 530 条能力缺口按日期代数、时序事件、排名组合、约束和数据域分簇；只开发能覆盖一类语句的通用节点或规则。
3. 对 53 条迁移数据缺口执行准入裁决：有完整权威成员关系的接入版本化数据；可由现有事实表确定推导的实现派生规则；歧义、噪声和赛题域外项保持拒绝。
4. Web/API 已显示正式流水线分段耗时、SQL、IR、诊断和证据状态；最终答辩材料阶段再按封板 HEAD 做一次浏览器截图核验。
5. 删除不再被调用的兼容模块前，先采集调用关系和差分覆盖；连续稳定后按包删除，不做一次性大拆除。

### P2：非竞赛阻塞的产品化增强

- API 鉴权、配额、审计日志和敏感配置生命周期。
- 多实例并发、背压、资源限额和超时策略。
- 指标、日志、追踪、告警及运行手册。
- Doris 多节点高可用、备份恢复、滚动升级和灾难演练。

这些项目有助于生产部署，但不应挤占赛题 P0/P1 的正确率、扩展性和真实性能封板。

## 3. 每个能力族的标准流程

1. 从全量语料生成最小失败簇，记录统一错误码和共同语义。
2. 判断应修改 Grammar、Typed AST、Binder、Logical IR、Rule、Physical Strategy、Backend 还是数据目录。
3. 先写一个最小正例、一个负例、一个边界例和一个跨能力组合例。
4. 在正确层实现通用节点或规则，禁止匹配 Excel 行号、完整 DSL 或单个证券名称。
5. 跑局部测试、全量测试、官方漏斗差分和架构边界。
6. 在 Doris 上与独立 reference SQL 比较完整结果，并采集 P95/EXPLAIN/Profile。
7. 只有受影响语料均闭环且未制造新退化时，才更新当前证据。

## 4. 最后一轮核心开发方案

本轮不扩大产品边界，只补齐会直接影响金融语义可信度、评委隐藏测试和现场解释力的四项契约。实现必须进入现有正式编译链，不能建立第二套旁路。

### 4.1 历史有效期贯穿

外部范围目录已经保存 `effective_from` 和 `effective_to`。DSL 明确给出日期时，物理 IR 中的外部成员判断显式携带行情行 `bizdate`，Doris 后端生成 `effective_from <= bizdate` 且 `effective_to >= bizdate` 的约束，空边界表示未知起点或持续有效；日期为空时只绑定指定 `snapshot_id`，明确表示当前快照口径，不凭空推断历史时点。指数、行业、概念和 T+0 规则使用同一通用节点，不在规划器里增加名称特判。

验收条件：

1. 历史日期只命中当日有效成员，不能使用当前快照倒推历史。
2. 不具备 `effective_dating` 能力的资源不能接收生效时点。
3. 生成 SQL、Physical IR 和结构化 EXPLAIN 均能看到该约束。
4. 当前仅有快照口径的数据继续绑定 `snapshot_id`，不伪造完整历史。

### 4.2 加速资源新鲜度进入选路

前缀表和物化汇总必须与基础表具有一致的最大日期、最小日期、交易日数和行数，才能作为活动候选。统计缺失或水位不一致时，候选保留在 EXPLAIN 中，但标记为不可选择并回退 RAW；显式测试模式仍可选择 shadow 候选用于差分验证。水位判断集中在统计快照对象中，规划器不复制比较逻辑。

验收条件：

1. 新鲜加速表维持当前 PREFIX/MV 选择结果。
2. 任一关键水位不一致时自动选择等价基线，并给出稳定原因码。
3. 缺统计不能静默视为新鲜。
4. 官方水位脚本继续作为运行前真实 Doris 门禁，编译期资格检查不替代数据库实测。

### 4.3 金融规则发布治理

`FinancialRuleCatalog` 从“规则列表”提升为不可变发布单元。发布元数据至少包含发布 ID、状态、生效时间、审批标识、上一版本和回滚目标。正式编译上下文只接受 `active` 且已生效、未过期的发布；候选配置通过独立校验入口检查来源角色、发布迁移、规则版本和回滚链，不支持在请求处理中热改文件。

验收条件：

1. 活动发布可以加载并进入上下文指纹和 API 目录。
2. draft、shadow、retired、未来生效和已过期发布不能成为正式上下文。
3. 候选发布必须指向当前发布，且规则降版、规则无说明删除和无效回滚目标会失败。
4. 校验报告包含基线/候选指纹、变更规则和确定性门禁结果。

### 4.4 逐查询能力协商

服务新增只分析、不执行的能力协商入口。它复用正式编译链，将结果统一归类为 `SUPPORTED`、`DATA_UNAVAILABLE`、`INVALID_INPUT` 或 `CAPABILITY_GAP`，并返回阶段、原因码、修复建议；成功时返回函数族、指标、所需资源、金融规则、路由和计划 ID。该接口不降低严格编译标准，也不把拒绝伪装为支持。

验收条件：

1. 支持查询与正式 `/v1/compile` 使用同一计划和上下文。
2. 缺数据、非法输入和未实现能力得到不同稳定类别。
3. 接口受现有鉴权、限流、并发和审计机制约束。
4. 不返回内部异常栈、凭据或原始用户 DSL。

### 4.5 复用现有端到端证据

现有 Hero Query 已同时覆盖 `CONS + EXIST + then + rank + 区间 + 市场集合运算`，无需重写。完成上述四项后，只补充历史成员和水位回退用例，再运行 Hero Query、240 条正式正确率、48 条性能矩阵和五类长周期门禁。开发期间使用定向测试，封板时只做一次完整重采。

## 5. 模块归属与禁止事项

| 需求 | 唯一实现位置 | 禁止做法 |
| --- | --- | --- |
| 历史成员关系 | `physical.ir`、`physical.planner`、`backend.doris` | 在名称映射或 SQL 字符串后处理里补条件 |
| 加速新鲜度 | `physical.statistics`、候选决策函数 | 在每条策略中复制日期比较 |
| 规则发布 | `financial_rules` 与单一候选校验脚本 | 引入数据库配置中心或微服务 |
| 能力协商 | `service`、`api` | 建立宽松编译旁路 |
| 复杂组合证据 | 现有 `hero`、correctness、performance | 再造一套演示编译器 |

本轮不接入交易执行，不构建自然语言模型，不增加 Kafka、Redis、Kubernetes 或新的前端框架，不逐条为 5799 语料添加特殊分支。公开数据只在来源、许可、快照和有效期可审计时进入增强配置。

## 6. 封板前剩余事项

核心功能和机器证据已封板，只保留以下事项：

- 全部官方功能要求有代码、测试和可复核路径；不能实现的输入有合理且稳定的边界说明。
- 最终封板采用单一冻结提交：先提交源码，再统一重采正确率、编译 P95、48 条执行矩阵、五类长周期、能力矩阵、盲扩展和 Hero Query，最后生成不进入源码历史的匿名交付包。
- 证据刷新必须在核心代码提交后执行，生成物中的 Git HEAD、配置指纹、数据指纹和 Doris 水位必须一致；证据刷新提交只允许改变报告和元数据，不允许再改核心行为。
- 保留 53 条数据依赖迁移缺口的拒绝与审计，不为提高表面成功数伪造成员关系。
- 操作手册、PPT、图表、截图和视频按用户要求留到核心项目封板后统一制作。

满足这些条件后，再一次性制作操作手册、PPT、图表、截图和视频。最终材料只引用封板证据，不再反向推动核心开发。
