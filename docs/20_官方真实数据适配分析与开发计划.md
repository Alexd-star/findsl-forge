# 第20章 官方真实数据适配分析与开发计划

本文档记录 2026 年 6 月 9 日新取得的官方赛题组真实资料对 FinDSL Forge 项目的影响、完成度判断、关键差距和下一步开发计划。文档面向开发、验收和答辩三类场景：开发人员可以据此改代码，验收人员可以据此核查证据，答辩人员可以据此解释为什么项目从“样例验证”进入“官方数据验证”阶段。

## 20.1 当前结论

目前项目已经具备稳定的编译器内核、Doris SQL 生成器、prefix-sum 优化路径、SQLite/Pandas 等价验证、Doris 集群证据、可视化证据包、中文文档和答辩 PPT。上一阶段的证据证明了一件很重要的事：我们不是让大模型直接写 SQL，而是用确定性编译器把受控 DSL 编译为可验证的 SQL，并用测试和 Doris 证据约束正确性与性能。

新官方资料改变了项目的主战场。之前项目使用的是自定义内部 DSL，例如 `filter(indicator("close") > 10)`，表结构也围绕 `daily_quote / money_flow / stock_universe` 三类样例表展开。官方资料给出的真实 DSL 是槽位函数表达式，例如 `indicator('深', '', '个人持有比例', '5日内', '', '', '') > 5% and rank(...) <= 10`，真实数据表则是 `newzl.hsj_stock_code_info`、`newzl.hsj_stock_hq_basic`、`newzl.hsj_stock_hq_ext`。这意味着后续不能只补几条样例，而要新增官方槽位 DSL 前端、官方字段映射、官方 Doris 导入脚本、官方训练语料解析覆盖率报告和真实数据 SQL 验证路径。

因此，当前项目状态应判断为：基础工程能力完整，旧证据链完整，但官方真实数据适配尚未完全完成。若以最终比赛提交为目标，后续优先级应从“扩展示例功能”转为“官方槽位 DSL 与官方三表数据的端到端闭环”。

## 20.3 官方 DSL 规范解读

官方 DSL 的核心是“槽位函数 + 比较表达式 + 逻辑连接”。其函数不是普通 SQL 函数，而是对金融选股语义的抽象。系统需要先把自然语言理解为这些槽位，再把槽位函数编译成 Doris SQL。

官方候选函数包括：

| 函数 | 语义 | 编译关注点 |
|---|---|---|
| `indicator` | 取某市场、范围、指标、日期、标的类型、聚合方式、出现次数下的指标值 | 最核心函数，需要映射到字段、表、日期过滤、市场过滤、范围过滤和聚合 |
| `rank` | 对指标排名 | 需要生成 `ROW_NUMBER()` 或 `RANK()`，并处理升降序、前十、后十、百分比排名 |
| `belong_industry` | 按所属行业计算指标 | 需要 join 代码表行业字段，并按行业聚合 |
| `queryData` | 查询某标的某指标值 | 需要用 `name/tgtcode/tztcode` 定位标的 |
| `cross_above/cross_down` | 上穿/下穿 | 需要窗口 `LAG()` 比较前后两日相对关系 |
| `close_together` | 指标粘合 | 需要定义可解释阈值，若官方未给阈值应标记为可配置 |
| `reset` | 回调到某指标 | 需要前序偏离和当前接近的组合判断 |
| `golden_cross` | 金叉 | 通常等价于短周期指标上穿长周期指标 |
| `record_high/record_low` | 创某周期新高/新低 | 可用窗口 `MAX/MIN` 或官方字段 `pxMkTopDays/pxMkBotDays` |
| `position` | 指标处于周期高中低位置 | 需要区间分桶，可用窗口 min/max 与当前值归一化 |

官方参数中最关键的是 `market/filter_scope/indicator_name/date/select_type/agg_func/count_exp/period`。其中 `market` 不是股票代码字段，而是沪、深、京、创业板、科创板等范围语义；`filter_scope` 必须从原文直接抽取，不能擅自改写；`indicator_name` 需要从候选指标中匹配，存在 `N/X/STR` 占位符；`count_exp` 用 `CONS/EXIST` 表达连续或出现次数；`then` 只应该在进入 `rank` 前使用，表示先筛选再排名。

这套 DSL 的难点并不在语法，而在语义压缩：同一个 `indicator` 函数可能对应代码表字段、基础行情字段、衍生行情字段、生成列、窗口指标、布尔派生指标或暂未出现在官方三表中的指标。项目需要把“可落到官方三表的指标”与“规范中存在但本批数据无法直接计算的指标”区分清楚，不能为了覆盖率硬生成假 SQL。

## 20.4 与当前项目的差距

当前项目的主要优势是编译器工程链条成熟，主要不足是 DSL 前端和数据模型仍偏上一阶段样例。差距如下。

| 项目 | 当前状态 | 官方真实数据要求 | 差距等级 |
|---|---|---|---|
| DSL 语法 | 支持内部 DSL，如 `filter(indicator("close") > 10)` | 支持官方槽位 DSL，如 `indicator('沪', '', '最新价', '今天', '', '', '') > 10` | 高 |
| 字符串 | 当前词法器只支持双引号 | 官方语料使用单引号 | 高 |
| 逻辑连接 | 当前使用 `&/^/|`，函数式 `then(...)` | 官方使用英文 `and/or/then` 以及 `limit x,y` | 高 |
| 数值表达 | 当前支持普通数值 | 官方有百分号、中文时间、`~=`、`between`、单位换算 | 高 |
| 数据表 | 当前配置是 `daily_quote/money_flow/stock_universe` | 官方是 `hsj_stock_code_info/hq_basic/hq_ext` | 高 |
| 指标配置 | 当前只有少量样例指标 | 官方表结构有 142 个字段，训练语料高频指标超过百个 | 高 |
| SQL 目标 | 当前 SQL 面向样例表并用 `ts_code/trade_date` | 官方主键为 `mktcode/tgtcode/bizdate` | 高 |
| 性能证据 | 已有 Doris 5M 合成数据 36.24x 证据 | 应补官方 CSV 导入后的真实数据 benchmark | 中高 |
| 文档证据 | 中文文档/PPT/截图包齐全 | 需要新增官方真实数据适配说明和验收截图 | 中 |

这意味着下一步最关键的开发目标不是重写旧系统，而是增加一个“官方槽位模式”。它可以和内部 DSL 模式并存：内部 DSL 继续承担可控编译器回归测试，官方槽位模式承担比赛真实输入、真实数据、真实 Doris SQL 交付。

## 20.5 技术路线

推荐采用“四层适配”方案。

第一层是官方槽位 DSL 解析器。新增独立模块读取官方 `slot_dsl`，支持单引号字符串、百分数、`and/or/then`、比较、四则运算、函数调用、`between`、`limit` 和布尔字面量。解析结果应输出标准 AST，并提供 JSON 展示，方便答辩解释。

第二层是官方指标注册表。根据 `stock_schema_tables.md` 和 CSV 表头生成 `configs/official_tables.json` 与 `configs/official_indicators.json`。第一批必须覆盖真实三表中能直接落地的核心指标，如最新价、开盘价、最高价、最低价、收盘价、成交量、成交额、换手率、量比、涨跌幅、涨停、跌停、连板天数、主力净流入、主力买入/卖出、3/5/10 分钟涨速、集合竞价金额、ST、沪股通、深股通、科创板、创业板等。对财务类、概念类、题材类、相似 K 线等本批数据没有字段支撑的指标，应输出明确诊断，不生成伪 SQL。

第三层是官方 SQL 生成器。它不必完全复用内部 DSL 的 SQL 生成器，因为两套 AST 语义不同。官方 SQL 生成器应以 `hsj_stock_hq_basic` 为行情骨架，按需 left join `hsj_stock_hq_ext` 和 `hsj_stock_code_info`，统一输出 `mktcode/tgtcode/bizdate/name`。排名使用 Doris 窗口函数，日期范围尽量下推到基础 CTE，能够使用官方已有派生字段时优先使用字段，无法直接字段化的 rolling 指标再使用窗口计算。

第四层是真实数据 Doris 证据。新增脚本按官方 DDL 建库建表，使用 Stream Load 导入三张 CSV，生成基础行数、日期范围、字段非空率、样例 SQL、官方 DSL 样例编译覆盖率、Doris EXPLAIN 与耗时报告。Apache Doris 官方文档中 Stream Load 适用于通过 HTTP 将本地文件导入 Doris；Unique Key 模型适合按主键更新/去重；物化视图可做透明改写，但窗口函数场景仍应保留显式 prefix/特征表路径。因此本项目后续应以 Stream Load + Unique Key + 显式特征表作为主线。

## 20.6 开发计划

### 阶段一：官方资料入库与可审计画像

目标是让项目能稳定识别官方资料，不依赖开发者口头说明。

需要新增：

- `configs/official_data_sources.json`：记录官方资料路径、文件名、表名、行数、列数、日期范围和文件大小。
- `scripts/profile_official_data.py` 或 CLI 子命令：扫描官方 CSV 和 Excel，生成 JSON/Markdown 画像。
- `reports/official_data_profile.md`：写入三表行数、字段、日期范围、训练语料函数分布、指标高频统计。

验收标准：

- 能在不读取全量 CSV 到内存的情况下完成画像统计；
- 能明确输出 `hsj_stock_hq_basic=13650347`、`hsj_stock_hq_ext=6170822`、`hsj_stock_code_info=5686`；
- 能输出 Excel 5799 条训练语料和高频函数分布；
- 报告中标注哪些字段可直接映射，哪些指标暂不可落地。

### 阶段二：官方槽位 DSL 解析器

目标是让项目能解析官方 `slot_dsl`，至少先完成语法层覆盖。

需要新增：

- `src/findsl/official_slot.py`：官方 DSL 词法、解析、AST、SQL 编译入口。
- `tests/test_official_slot.py`：覆盖单引号、百分号、`and/or/then`、`rank`、`between`、`limit`、`queryData`、四则运算。
- CLI 子命令 `official-slot-parse` 和 `official-slot-compile`。

验收标准：

- 官方 Excel 前 100 条 `slot_dsl` 能完成语法解析；
- 对无法映射到真实字段的指标给出 `UNSUPPORTED_OFFICIAL_INDICATOR` 诊断；
- 对可映射指标能输出 Doris SQL；
- 解析器不影响旧 DSL 的 203 个测试。

## 20.7 风险与答辩口径

第一，不能再说“官方要求全部完成”。更准确的说法是：项目原编译器和证据链已经完成，官方真实数据到位后正在进行官方槽位 DSL 与官方三表适配。适配完成后，才能用官方数据重新刷新最终证据。

第二，不能把合成数据 36.24x 说成官方数据性能。正确口径是：合成 Doris 证据证明 prefix-sum 优化路径在 500 万行长窗口场景有效；官方数据到位后，应复用同一证据采集器在 `hsj_stock_hq_basic/hsj_stock_hq_ext` 上重跑，以形成最终比赛证据。

第三，不能对所有官方训练语料强行生成 SQL。官方训练语料包含财务、基金、概念、相似 K 线、题材、龙虎榜、财报期等指标，本批官方三表并不全部包含这些数据。成熟做法是把这些样例解析出来，明确标注“语法可解析、数据不可落地”，并给出缺失字段清单。

第四，官方 DDL 和 Markdown 存在少量字段名差异，例如文档里有 `quanRatio`，CSV 和 DDL 中是 `quantRatio`；文档里包含 `marketValue/listedMarketValue/risePct/avgPx` 生成列说明，但 DDL 文件未显式建这些列。后续实现必须以 CSV 表头和实际 DDL 为准，同时在报告里记录差异。

## 20.8 下一步执行顺序

推荐立即执行以下开发顺序：

1. 新增官方槽位 DSL 解析器测试，先证明当前项目无法解析官方 DSL。
2. 新增 `official_slot.py`，完成语法解析和可映射指标 SQL 生成。
3. 新增官方表和指标配置，首批覆盖真实三表直接字段。

第一是官方数值单位缩放。`hsj_stock_hq_basic.csv` 中 2026-04-14 的 `lastPx` 中位数约为 159800，按 A 股价格语义应理解为 15.98 元量级；`turnRatio`、`pBR`、`dynPE`、`callAucRisePct`、`ZJLXMainTradeVolPer` 等字段也呈现出 10000 倍缩放特征。如果把 DSL 中的“最新价小于 30”“市净率小于 2”“涨幅大于 5%”直接编译成 raw 字段比较，SQL 可以执行但结果会严重偏离业务含义。当前已将价格类字段统一转为 `字段 / 10000.0`，涨跌幅转为 `((lastPx - preClosePx) * 100.0 / preClosePx)`，比例/估值类字段转为 `字段 / 10000.0`，总市值和流通市值转为缩放后的价格乘股本。

## 20.11 2026-06-09 第三阶段：窗口语义增强

本阶段专门处理官方 DSL 中最容易“看起来能编译、实际语义不对”的槽位：`agg_func` 和 `count_exp`。官方说明把 `agg_func` 定义为 `MAX/MIN/AVG/SUM/GROWTH_RISE/GROWTH_FALL`，把 `count_exp` 定义为 `CONS/EXIST + 比较符 + 次数 + 单位`。如果编译器只是读取当前行字段，就会把“近 5 日平均成交量”“至少 3 日涨幅超过 5%”“连续每日成交量下跌”误译成单日条件，结果虽然能跑，但不具备答辩可信度。

当前已完成的实现包括四部分。

第一，`AVG/SUM/MAX/MIN` 被编译为按 `mktcode/tgtcode` 相关的窗口聚合子查询。例如 `indicator('', '', '成交量', '近5日', '', 'AVG', '') > 1000` 会生成 `SELECT AVG(wb.volume) ... WHERE wb.mktcode = base.mktcode AND wb.tgtcode = base.tgtcode AND wb.bizdate BETWEEN ...`，外层再固定到窗口结束日。这样可以避免同一股票在窗口内重复输出多行，也能把日期范围下推到子查询。

第二，`EXIST/CONS` 被编译为计数子查询。例如 `indicator('', '', '涨幅', '近5日', '', '', 'EXIST>=3日') > 5%` 会统计近 5 日内满足涨幅条件的交易日数量，并与 3 比较；`CONS=每日` 会要求窗口内所有有效交易日都满足条件。对于 `CONS=3日` 这类“最长连续段”语义，当前先按阈值计数落地并给出 warning，后续应在 Doris 特征表中增加连续段计算以做精确优化。

第三，`GROWTH_RISE/GROWTH_FALL` 被编译为首尾变化率。实现使用 Doris 聚合思路中的 `MIN_BY(value, bizdate)` 与 `MAX_BY(value, bizdate)` 取窗口首日和末日对应值，再计算 `(末值 - 初值) / abs(初值) * 100` 或 `(初值 - 末值) / abs(初值) * 100`。这与项目已有的涨幅百分数口径保持一致，也比直接用最大值减最小值更符合“变化率/增长率”的语义。

第四，`agg_func + count_exp` 被拆成“按时间粒度分桶后聚合，再统计满足条件的 bucket 数”。例如 `AVG + EXIST>=3日` 会按日生成 `bucketed.agg_value`，统计满足比较条件的日 bucket；`GROWTH_FALL + CONS=每日` 会使用 `LAG(value) OVER (...)` 计算相邻交易日变化，确保“逐日下跌”不是被误写成全窗口下跌。

该阶段结束时覆盖率是 `parse_ok=5792`、`parse_failed=7`、`compile_ok=1411`、`compile_failed=4381`。随后第四阶段继续处理 period、行业聚合和 rank-count，覆盖率已进一步提升，见下一节。

## 20.12 2026-06-09 第四阶段：真实语义纠偏与覆盖率提升

第四阶段处理的是覆盖率报告中“能编译但可能不可信”或“官方三表明明可以支撑但尚未落地”的问题。新增内容全部按 TDD 执行，先补失败测试，再实现，再刷新官方 workbook。

第一，`record_high/record_low` 不再把 `MAX(...) OVER (...)` 或 `MIN(...) OVER (...)` 直接放进普通 WHERE 条件。这个旧写法在 Doris/MySQL 类 SQL 中很容易变成不可执行 SQL。现在价格类创新高/创新低优先使用官方衍生表 `hsj_stock_hq_ext` 的 `pxMkTopDays/pxMkBotDays`；例如 `record_low('', '', '', '120日', '零四年', '', '', '') = True` 会生成 `ext.pxMkBotDays >= 120`。对非价格但已映射的数值指标，系统使用合法的相关聚合子查询完成窗口 MAX/MIN 判断。

第二，新增 `position(...)` 的可落地子集。默认指标为空时按“最新价”处理；对已映射的数值指标，系统在指定 period 内取同一股票的窗口最小值和最大值，把当前位置划分为 `最低/低/中/高/最高` 五档。这个实现不是简单字符串匹配，而是用 CASE 表达式和窗口相关子查询计算相对位置。对于 period 无法精确解析的表达，系统会给出 warning，并退化为历史至当前窗口，不伪造更细时间语义。

第三，修复跨日期 `and` 的根因错误。旧逻辑会把 `indicator(..., '零三年') > ... and indicator(..., '零四年') = True` 的两个日期条件都提升到同一条 `base` 行，形成 `base.bizdate BETWEEN 2003... AND base.bizdate BETWEEN 2004...` 这种不可能满足的 SQL。现在当 AND 两侧存在互斥日期槽位时，编译器会把每个分支转为 correlated `EXISTS`，用同一 `mktcode/tgtcode` 关联股票身份，让“2003 年满足条件且 2004 年满足另一个条件”成为可执行语义。

第四，新增 `belong_industry` 的官方三表可支撑子集。代码表中存在 `hyBlkRefName`，因此 `belong_industry('', '', '市盈率', '', 'AVG')` 会被编译为同一行业内 `pETTM` 的平均值子查询，并通过 `wc.hyBlkRefName = code.hyBlkRefName` 与当前股票行业关联。该函数只对官方三表中已映射的数值/时间指标开放；财务、基金、龙虎榜等缺失数据域仍保持稳定错误码。

第五，新增普通 `rank(..., count_exp)` 的分桶排名语义。对于 `rank('', '', '收盘价', 'desc', '近5日', '', '', 'EXIST>=3日') <= 3`，系统先按 `DATE_TRUNC(rb.bizdate, 'day')` 分桶计算每日排名，再统计同一股票有多少个 bucket 满足 `rank_no <= 3`。`CONS=每日` 会要求所有有效 bucket 都满足排名条件。带 `agg_func` 的 rank-count 仍暂不强行落地，因为它更适合通过 Doris 物化特征表或离线 rank feature table 来保证性能和语义。

## 20.14 2026-06-09 第六阶段：复合相对日期落地

第六阶段修复的是一个覆盖率数字不一定变化、但 SQL 可信度会明显变化的问题。官方 workbook 中有不少时间槽不是单独的“今天、昨天、近三日、2024年”，而是“某个基准时间段的前/后/第 N 个时间单位”。如果编译器把这类表达都降级成 `1=1`，样例仍然可能算作“编译成功”，但生成 SQL 实际上丢掉了日期约束。对高性能 Doris SQL 来说，这会造成两个后果：一是扫描范围变大，二是筛选语义变宽，答辩时很难解释结果为什么可信。

本阶段在 `src/findsl/official_time.py` 中增加了内部 `_DateInterval(start, end)` 模型。简单时间先被归一成区间或单日，复合时间再基于这个区间做“前 N、后 N、第 N”的偏移。这样“昨天的前1日”在有交易日历时会回退到前一个交易日 `2026-04-10`；“本月的前一周”会从本月起点 `2026-04-01` 往前取 7 个自然日，得到 `2026-03-25` 至 `2026-03-31`；“2012年的后4年”会排除 2012 年本身，得到 `2013-01-01` 至 `2016-12-31`；“一二年的第4年”和“2018年的第五年”则按基准年份的包含式序号分别得到 2015 年和 2022 年。随后又补齐了官方真实样例中出现的显式年份区间，例如“2006年-12年”“2006年至12年”“06年到12年”，统一归一到 `2006-01-01` 至 `2012-12-31`。

对“最近的第二天”这类表达，本阶段按官方锚点日期和交易日历处理，而不是按自然日盲退。以 `2026-04-14` 为锚点、交易日历为 `2026-04-09/2026-04-10/2026-04-13/2026-04-14` 时，“最近的第二天”归一为 `2026-04-13`。链式表达“最近的第二天的后3日”会先得到 `2026-04-13`，再尝试向后取 3 个交易日；由于官方数据锚点停在 `2026-04-14`，最终 SQL 裁剪为 `base.bizdate = '2026-04-14'`，同时保留“已裁剪到官方可用数据”的 warning。对完全落在锚点之后的“本周的后3日”，系统直接输出 `1=0` 和“没有官方行可满足”的 warning，不再用 `1=1` 静默放宽条件。

本阶段新增和更新了两层测试。`tests/test_official_time.py` 验证时间归一化本身，包括“2006年-12年”“06年到12年”“昨天的前1日”“本月的前一周”“2012年的后4年”“一二年的第4年”“2018年的第五年”“最近的第二天”和“最近的第二天的后3日”。`tests/test_official_slot.py` 进一步验证这些时间槽进入官方 DSL 编译器后，会生成具体 `base.bizdate` 条件、`BETWEEN` 条件或 `1=0`，而不是退回 `1=1`。最新验证命令为：
