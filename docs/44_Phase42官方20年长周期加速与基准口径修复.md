# Phase 42 官方 20 年长周期加速与基准口径修复

## 1. 本阶段解决的问题

赛题要求长周期查询相对全表扫描至少提升 10 倍。项目早期的 500 万行演示库给出过 `36.24x`，但那套数据只覆盖约三年；官方真实数据覆盖 `2006-01-04` 至 `2026-04-14`，原报告却只有约 `1.17x`。两份数字并不矛盾，它们来自不同表布局和测量脚本，但后者会让评委质疑项目是否真正完成了“19 年以上”这一关键指标。

复查后发现，官方准备脚本的文字说明写着关闭 SQL Cache，实际 MySQL 连接没有执行 `SET enable_sql_cache=false`。同一条窗口查询连续运行时，Doris 可以直接返回缓存结果，基线成本被严重压低。这个问题不是优化算法失效，而是基准方法没有落实自己的实验条件。Phase 42 修复连接级缓存设置，并增加独立的 Query Profile 采集器，每一次正式运行都从 Profile 中反查 `Is Cached: No`。

## 2. 表布局与优化路径

优化表 `newzl.hsj_stock_hq_basic_rollup` 是一张窄型滚动特征服务表。它保留官方基础行情的 `(bizdate,mktcode,tgtcode)` 稳定键和已经验证过的 `volume_sum_5`、`volume_sum_20`、`turnover_sum_20`，不复制无关宽字段。表使用交易月自动分区，共形成 244 个分区，并继续按证券键哈希分桶。精确交易日查询因此只访问一个月份，而不是读取 20 年全表后再做排序、窗口聚合和末日过滤。

这项设计遵循 Doris 官方建议的“少读数据”原则。日期条件直接作用于分区列，EXPLAIN 必须出现 `partitions=1/244`；如果条件被函数包裹、类型不匹配或没有下推，证据脚本会判定失败。部署 SQL 位于 `deploy/doris/official/06_partitioned_rollup_serving.sql`，由官方环境准备脚本统一执行，数据来源仍是完整前缀特征表，不存在另外构造的比赛答案表。

Apache Doris 对分区裁剪、数据裁剪和 Query Profile 的官方说明分别见：

- [Partition Pruning Optimization](https://doris.apache.org/docs/4.x/query-acceleration/tuning/tuning-plan/optimizing-table-scanning/)
- [Data Pruning](https://doris.apache.org/docs/4.x/key-features/data-pruning/)
- [Query Profile Analysis Guide](https://doris.apache.org/docs/4.x/query-acceleration/query-profile/)
- [Auto Partitioning](https://doris.apache.org/docs/4.x/table-design/data-partitioning/auto-partitioning/)

## 3. 正确性与性能证据

正式实验使用官方 `13,650,347` 行基础行情，基线在全历史上计算 20 日成交量滚动和，再筛选 `2026-04-14`；优化路径直接读取同日已物化的滚动特征。两边均按稳定键排序后输出完整结果，而不是只比较 `COUNT(*)`。7 轮正式运行得到 5,487 行，完整结果 SHA-256 均为 `427ef0387f97b245a439152246003e4beaa13a8acc669ffd06559d5f8eba5ac6`。

Query Profile 的基线中位耗时为 `964 ms`，优化路径为 `23 ms`，服务端加速 `41.913x`。基线 P95 为 `1020 ms`，优化 P95 为 `33 ms`。所有轮次均关闭 SQL Cache，基线与优化按交替顺序执行，避免固定先后顺序把热机状态偏向某一方。EXPLAIN 显示基线扫描 `1/1` 全表分区，优化路径扫描 `1/244` 单月分区。

通用官方准备脚本使用客户端端到端计时，修复缓存设置后 5 轮平均值为：基线 `1066.576 ms`，优化 `83.196 ms`，加速 `12.82x`。该数字包含 MySQL 客户端启动和传输开销，因此低于服务端 Profile 的 `41.91x`。交付材料保留两种口径并标明测量边界，不用其中一个替换另一个。

## 4. 自动门禁

`scripts/collect_phase42_long_horizon_evidence.py` 会依次检查基础表与服务表行数、日期范围、分区数量、Doris 版本、完整结果哈希、每轮缓存状态、任务状态、Profile 总耗时和 EXPLAIN 分区比例。任一条件不满足都会以非零状态退出。正式 JSON 与 Markdown 报告位于 `reports/phase42_long_horizon_doris.*`，导出后进入 `submission_artifacts/evidence_snapshots/`。

复现命令如下：

```powershell
$env:PYTHONPATH = "src"
python scripts/collect_phase42_long_horizon_evidence.py `
  --warmups 1 `
  --repeats 7 `
  --min-speedup 10 `
  --json-output reports/phase42_long_horizon_doris.json `
  --report-output reports/phase42_long_horizon_doris.md
```

## 5. 与赛题评分点的关系

本阶段直接补强“19 年以上长周期”“前缀和等加速路径”“至少 10 倍”“SQL 不高于 10 秒”四个评分点。`41.91x` 证明数据库内部执行收益，`12.82x` 证明从客户端观察仍超过门槛，完整结果哈希证明优化前后语义一致，单分区 EXPLAIN 证明收益来自可解释的表设计和计划选择，而不是结果缓存或删减数据。

这张服务表目前覆盖已经物化的固定滚动窗口。任意窗口仍应回退到累计前缀差分，未配置的数据域继续输出结构化诊断。后续优化器工作应把“固定窗口服务表、任意窗口前缀差分、原始窗口函数”作为三个可比较候选，根据日期约束、窗口是否物化和目录统计选择路径；不能把所有请求强制改写到同一张表。
