## 2. 1 分钟项目介绍稿

各位老师好，我们的项目是 FinDSL Forge，面向赛题 19“将选股 DSL 编译成高性能 Apache Doris SQL”。项目解决的问题是：金融选股需求经常包含市场过滤、连续条件、窗口统计、每日排名和日期范围，如果直接手写 SQL，容易出错，也难以保证性能。我们设计了一套受控 DSL，把选股条件先表示成结构化语言，再由确定性编译器生成 Doris SQL。

项目不是让大模型直接生成 SQL。中文输入和可选大模型只负责提供 DSL 候选，所有候选都必须经过语法解析、语义校验、Doris SQL 安全检查和 SQL/reference 等价验证。对于 120 日成交量这类长窗口查询，我们实现了 prefix-sum 优化，并保存了 Doris 5,000,000 行证据，当前加速比为 36.24x。项目当前 readiness 显示 Blocking gates PASS、Warning count 0、pytest 197 passed、官方正例 37/37、负例 37/37，具备可复核、可回溯的提交证据。

## 3. 3 分钟项目讲解稿

本项目可以从三个层次理解。

第一层是业务输入层。用户可以直接写 DSL，也可以输入中文选股需求，例如“筛选 A 股连续三天主力净流入为正并按换手率排名前一百”。系统会把中文需求转换成受控 DSL 候选，但不会直接执行大模型给出的 SQL。

第二层是编译与验证层。核心入口是 `Compiler.compile()`。它会先调用 parser 生成 AST，再由 semantic analyzer 检查指标、函数、窗口、rank 参数是否合法，然后由 SQL generator 生成 Doris SQL。生成 SQL 后，还要经过 Doris SQL validator，防止未知表、多语句、危险 SQL 等问题。为了证明 SQL 语义正确，项目使用 Pandas reference evaluator 独立解释 DSL，再用 SQLite 执行生成 SQL，比较两边的股票代码和日期结果。

第三层是性能和交付证据层。赛题关心长窗口加速，因此项目对符合条件的 rolling SUM 使用 prefix-sum 优化。简单说，普通窗口每次都要重复计算过去 120 天，而 prefix 路径可以提前准备累计或物化窗口结果，查询时直接读取或做差。项目保存的 Doris evidence 显示，在 5,000,000 行数据上，120 日成交量查询从 baseline 平均约 5182 ms 降到优化后约 143 ms，加速 36.24x，同时行数一致。最后，readiness 脚本把 pytest、官方套件、Doris 证据、Demo smoke、Git 状态都汇总到提交包，保证材料不是口头承诺，而是可复核证据。

## 4. 核心算法讲解稿

核心算法可以用“编译 + 优化 + 验证”来讲。

编译部分从 DSL 字符串开始。lexer 把字符串拆成 token，parser 把 token 组织成 AST，semantic analyzer 判断 AST 是否符合金融选股语义。例如窗口必须是正整数，未知指标会被拒绝，rank 的 top、bottom、percent 不能乱用。校验通过后，SQL generator 根据 AST 生成 Doris SQL。

优化部分主要是 prefix-sum。对于 `SUM(indicator("volume"), 120)` 这种长窗口求和，如果指标配置中声明支持 prefix-sum，生成器会把普通窗口函数改写成 prefix 表路径。这样 Doris 查询不再每次重复扫描 120 日窗口，而是利用预先准备的窗口列或前缀结果。项目的 explain 会记录优化是否应用，Doris evidence 会记录 baseline 和 optimized 的实际耗时。

验证部分用 reference oracle。项目不只看 SQL 字符串是否长得对，而是把 DSL 用 Pandas 独立执行，再把生成 SQL 用 SQLite 在同一批样本上执行，最后比较结果集。如果 SQL 少了股票日期，就是 missing；如果 SQL 多了，就是 extra。只有 missing 和 extra 都为空，才认为语义一致。

当前证据摘要显示 Blocking gates PASS，表示提交前必须通过的检查全部通过。Warning count 为 0，说明没有未关闭的风险警告。Pytest 是 197 passed，表示项目已有 197 个自动化测试通过，覆盖解析、语义、SQL 生成、等价验证、Doris evidence、Demo、readiness 和证据摘要。

## 7. 评委可能追问的 30 个问题和回答

1. 问：你们是不是直接让大模型生成 SQL？  
   答：不是。大模型或中文入口只产生 DSL 候选，最终 SQL 由确定性编译器生成，并经过语义校验和等价验证。

2. 问：DSL 是什么？  
   答：DSL 是领域专用语言，本项目用它表达选股条件，例如 `filter`、`rank`、`SUM`、`RET`。

3. 问：为什么不直接写 SQL？  
   答：直接写 SQL 容易出错，难以统一验证和优化。DSL 可以限制表达范围，便于编译、安全校验和性能优化。

4. 问：AST 有什么用？  
   答：AST 是系统理解 DSL 后形成的结构树，证明项目不是简单字符串替换。

5. 问：正确性怎么证明？  
   答：用 Pandas reference evaluator 独立解释 DSL，再用 SQLite 执行生成 SQL，比较两个结果集。

6. 问：reference oracle 会不会也错？  
   答：任何实现都有风险，但 reference 与 SQL 生成器是独立路径，能显著降低同源错误。关键场景还有官方套件和人工核验。

7. 问：36.24x 是所有查询都能达到吗？  
   答：不是。它是 120 日成交量 rolling SUM 的 Doris 证据，不泛化到所有查询。

8. 问：为什么能加速？  
   答：长窗口 SUM 使用 prefix-sum 或物化窗口列，减少重复窗口计算。

9. 问：Doris evidence 是什么？  
   答：包含 Doris EXPLAIN、baseline/optimized 延迟、行数一致性和 speedup 的证据报告。

10. 问：如果指标新增怎么办？  
    答：普通指标优先在 `configs/indicators.json` 配置，尽量不改核心编译器。

11. 问：如果函数新增怎么办？  
    答：需要更新 `functions.json`、semantic、sqlgen、reference 和测试，因为函数涉及语义和 SQL 生成。

12. 问：负例有什么意义？  
    答：负例证明系统能安全拒绝错误输入，而不是崩溃或生成危险 SQL。

13. 问：Warning count 为 0 说明什么？  
    答：readiness 没有发现当前提交状态的风险警告，例如 Git dirty 或 Doris 证据缺失。

14. 问：Pytest 197 passed 能证明什么？  
    答：证明已有自动测试全部通过，但不能替代所有人工验收。

15. 问：Git HEAD 为什么重要？  
    答：它把证据和代码版本绑定，方便复现和回滚。

16. 问：真实行情样本在哪里？  
    答：在 `data/real_samples/eastmoney_a_share_sample/`，来自东方财富公开 K 线小样本。

17. 问：真实行情样本能证明性能吗？  
    答：不能。它证明业务字段和真实代码可运行，性能由 5M Doris 证据证明。

18. 问：Doris 环境现场能重跑吗？  
    答：可以，但依赖 Docker/Doris/MySQL client 环境。离线证据已保存，现场重跑需提前准备。

19. 问：SQL 安全怎么保证？  
    答：`doris_sql.py` 检查单查询形态、已知表引用、危险语句和窗口位置。

20. 问：LLM 直接输出 SQL 会怎样？  
    答：会被 `llm_adapter.py` 拒绝，不会进入执行链路。

21. 问：Demo 的作用是什么？  
    答：让评委直观看到中文输入、DSL、SQL、AST、Explain、结果和诊断。

22. 问：项目是否能脱离网络运行？  
    答：核心 CLI、测试和离线样本可以运行；真实 provider 和刷新外部行情需要网络。

23. 问：`reports/` 和 `submission_artifacts/` 区别？  
    答：reports 是本地生成目录，submission_artifacts 是提交和回溯用的轻量证据快照。

24. 问：Metadata warnings 是什么？  
    答：证据元数据解析时发现的问题。当前为 `<none>`。

25. 问：为什么要 evidence_summary？  
    答：它把关键证据数字集中到一页，便于评委快速核对。

26. 问：如果测试失败怎么办？  
    答：根据失败测试文件定位对应模块，例如 compiler、semantic、equivalence 或 readiness。

27. 问：是否存在硬编码？  
    答：测试样本固定是为了可回归；业务指标和表映射主要配置化，真实性能有 Doris 证据。

28. 问：项目最大亮点是什么？  
    答：确定性 DSL 编译、独立 reference 验证、prefix-sum 长窗口加速和完整证据链。

29. 问：项目不足是什么？  
    答：主要不足不是主链路缺失，而是边界证据还可以继续加厚：官方 12 类函数清单需要拿到 DSL 规范后逐项复核；简单数值函数已经有 ABS 模板配置证据，复杂时序函数还需要进一步模板化；更多官方问句和官方 20 年数据集需要到位后补跑完整 Doris benchmark。

30. 问：如果只能展示三样东西，你展示什么？  
    答：Web Demo、evidence_summary、Doris evidence。一个证明可用，一个证明总状态，一个证明性能。
