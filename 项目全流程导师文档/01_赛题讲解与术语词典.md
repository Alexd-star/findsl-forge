# 01 赛题讲解与术语词典

## 1. 赛题到底要解决什么问题

这个项目对应的是第五届中国研究生金融科技创新大赛“揭榜挂帅”赛题 19。官方参赛指南把本届比赛定位为金融科技领域国家级创新实践赛事，强调“真场景、真问题、真数据、真项目、真落地”。这句话对你很重要：评委不是只看一个能跑的页面，而是会看项目是否真的解决金融业务中的技术堵点，是否有可运行、可测试、可复核的工程成果。

赛题 19 属于“多模态技术与数据治理”赛道，发榜单位是华泰证券，题目全称是：

```text
行情选股 DSL 到高性能 Doris SQL 的自动化编译系统
```

项目内部文档把它概括为：

```text
Compile stock-screening DSL into high-performance Apache Doris SQL
```

翻成人话就是：把“选股条件”写成一种受控的小语言，也就是 DSL，然后让程序自动把这段 DSL 翻译成 Apache Doris 能执行的 SQL。Doris 是面向大数据分析的数据库，适合做很多股票、很多日期、很多指标的筛选和排序。赛题关注的不是做一个普通选股网页，而是做一个“能把业务规则稳定翻译成高性能数据库查询”的系统。

官方题面里还有一个关键表达：“解决自然语言转 DSL 后的最后一公里执行难题”。它的意思是，前端或智能问答系统可能已经把用户的话转成了 DSL，但数据库并不会执行 DSL。真正影响落地的是：这段 DSL 能不能被准确理解，能不能变成 Doris SQL，能不能在 19 年以上历史行情数据上跑得快，新增指标时能不能不反复改后端代码。

你可以把整个任务理解成这样：

```text
用户想法：筛选 A 股，连续 3 天主力净流入为正，再按换手率排名前 100
    ↓
受控 DSL：then(filter(market("A") & CONS(indicator("main_net_inflow") > 0, 3)), rank(indicator("turnover_rate"), desc, top=100))
    ↓
程序编译：词法分析、语法分析、语义校验、SQL 生成、安全检查
    ↓
Doris SQL：可以在 Doris 数据库里执行的查询语句
    ↓
验证结果：SQL 结果和独立 reference 结果一致，性能证据通过
```

## 2. 输入是什么

项目支持三类输入。

第一类是 DSL 文本。DSL 是一种项目自己定义的小语言，不是随便写自然语言，也不是随便写 SQL。例如：

```text
filter(SUM(indicator("volume"), 120) > 1000000)
```

它的意思是：筛选“近 120 日成交量滚动求和大于 1000000”的股票日期记录。

第二类是中文自然语言。项目里有 `src/findsl/nl2dsl.py`，可以把部分官方风格中文需求转换成 DSL 候选。例如“筛选 A 股连续三天主力净流入为正并按换手率排名前一百”会生成一个受控 DSL。注意，这不是让大模型直接写 SQL，而是先生成 DSL，再由编译器和验证器检查。

第三类是可选 LLM 候选。项目支持 OpenAI-compatible provider，但大模型只提供候选 DSL。项目会拒绝直接 SQL 和错误 DSL，这一点是答辩重点。

## 3. 输出是什么

项目的主要输出有四类。

第一类是 Doris SQL。它是数据库真正执行的语句，例如包含 `SELECT`、`JOIN`、`WHERE`、窗口函数或 prefix 表连接的 SQL。

第二类是 AST 和 explain。AST 是抽象语法树，用来证明程序真的理解了 DSL 结构。explain 是优化说明，例如是否使用了 prefix-sum 优化、是否做了日期下推。

第三类是验证报告。包括 `submission_readiness.md`、`official_suite_report.md`、`doris_cluster_evidence.md`、`evidence_summary.md` 等。

第四类是 Web Demo 展示结果。Web 页面可以展示中文输入、DSL、SQL、AST、Explain、结果行、错误诊断和证据。

## 4. 评判标准是什么

根据官方赛题 19 文本和参赛指南，评判不只看“有没有功能”，还会看技术任务完成度、量化指标、可运行性、技术文档和落地证据。官方题面中最关键的量化目标如下：

| 指标 | 官方目标 | 通俗解释 |
|---|---:|---|
| SQL 正确率 | >= 95% | 编译出来的 SQL 结果要和参考实现一致。 |
| 编译 P95 延迟 | < 50ms | 大多数 DSL 编译要很快。 |
| 长周期性能 | 19 年跨度查询加速 10x+ | 长历史查询不能全表硬扫，要用前缀和、物化视图或分区裁剪。 |
| 执行效能 | SQL 执行筛选结果不高于 10s | 生成的 SQL 真的要能在 Doris 里较快返回。 |
| 工程敏捷度 | 新指标/新函数核心编译引擎 0 行改动 | 业务扩展尽量走配置，不要每次改核心代码。 |
| 可运行交付 | 可运行、可测试、依赖清晰 | 参赛作品要能被组委会统一测试。 |
| 技术文档 | 技术路线、架构、实验、指标清晰 | 不能只交代码，还要讲清楚怎么做、为什么对。 |

当前项目的证据口径是：`197 passed`、官方风格正例 `37/37`、官方风格负例 `37/37`、Doris evidence `PASS`、Doris speedup `36.24x`、warning count `0`。这些数字能证明当前代码和证据包下的主链路质量，但答辩时不要把它们夸大成“所有未来题都一定通过”。尤其是 `36.24x`，它对应的是 5,000,000 行 Doris 数据上的 120 日成交量滚动 SUM，不代表所有查询都固定加速 36 倍。

## 5. 必须实现哪些功能

项目已经实现的核心功能包括：

1. DSL 解析：把文本拆成 token，再变成 AST。
2. 语义校验：检查指标名、函数参数、窗口大小、rank 参数是否合法。
3. SQL 生成：把 DSL 转成 Doris SQL。
4. SQL 安全验证：保证生成的是 Doris-safe 的单条查询，不是危险 SQL。
5. reference oracle：用 Pandas 独立解释 DSL，作为慢但可信的参考答案。
6. SQLite 本地执行：把生成的 SQL 在本地样本上执行，和 reference 比较。
7. prefix-sum 优化：对长窗口 `SUM` 使用前缀表，减少重复计算。
8. Doris evidence：在真实 Doris 兼容环境里采集 EXPLAIN、延迟、行数一致性和加速比。
9. 官方正负例套件：37 个正例、37 个负例。
10. Web Demo：让评委看见输入、DSL、SQL、AST、Explain、结果和错误诊断。
11. readiness 门禁：一次性检查测试、报告、Doris 证据、Git 状态等。
12. 证据导出：把本地 reports 导出到 `submission_artifacts/`，方便提交。

和官方题面逐项对应时，还要额外记住四个“攻关任务”：第一，构建高性能语义解析引擎，官方提到 ANTLR4 或同类工具、BNF 文法、12 类领域函数和标准 AST；第二，研发逻辑等价重写模块，重点是 CTE 嵌套与窗口函数自动化生成；第三，设计声明式规则驱动框架，把指标、表名、复权口径等业务约定配置化；第四，实现自适应查询优化器，对长周期查询自动走前缀和、物化视图或分区裁剪等加速路径。

当前项目对这些任务已经有主干实现，但有两个地方要诚实表达：项目使用的是递归下降 parser，可解释为“ANTLR4 或同类工具”中的同类解析器，但不是 ANTLR4 生成器；新指标配置化较强，简单数值模板函数已经通过 `ABS` 证明可配置扩展，复杂时序函数还需要进一步模板化。
