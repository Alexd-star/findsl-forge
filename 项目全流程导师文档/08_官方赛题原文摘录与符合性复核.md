# 08 官方赛题原文摘录与符合性复核

本文用于把官方参赛指南和赛题 19 题面中的关键要求，翻译成你能直接理解、能答辩、能验收的项目检查项。它不是替代官方文件，而是帮助你在答辩前确认：项目到底对上了哪些要求，哪些地方已经有证据，哪些地方还要等官方数据、模板或现场环境进一步确认。

## 1. 官方参赛指南关键信息

第五届中国研究生金融科技创新大赛是面向研究生群体的金融科技领域国家级创新实践赛事，指导单位包括教育部学位管理与研究生教育司、中国人民银行科技司，主办单位为中国学位与研究生教育学会。参赛指南强调本届赛事延续“揭榜挂帅”和自拟赛题两大赛道，并以“真场景、真问题、真数据、真项目、真落地”为核心导向。

这段话对本项目的直接影响是：不能把 FinDSL Forge 包装成一个普通课程作业，也不能只展示漂亮界面。评审会更关心它是否解决真实金融业务里的技术堵点，是否能运行、能测试、能解释、能复现，是否有数据、指标和工程证据支撑。因此项目材料必须围绕“可运行项目成果、技术文档、量化指标、演示视频、截图证据、Git 回溯”展开。

参赛指南还要求作品提交时包含精益画布、可运行项目成果、技术文档和原创性声明。可运行项目成果需要封装完整、依赖声明清晰，能够在标准环境下部署运行和测试。技术文档要系统阐述技术路线、模型架构或系统架构、关键技术细节、实验设计和量化指标。决赛阶段还要求演示 PPT，并在 PPT 中嵌入不超过 1 分钟的作品演示视频。

对应到当前项目，`README.md`、`PROJECT_INDEX.md`、`docs/`、`submission_artifacts/` 和 `项目全流程导师文档/` 已经覆盖了多数说明材料；`pyproject.toml`、`scripts/`、`deploy/doris/`、`data/` 和 `submission_artifacts/evidence_summary.md` 支撑可运行、可测试和可复核。仍需人工确认的是：最终精益画布模板、原创性声明模板、团队名称、提交压缩包命名、每个提交文件夹下的 `readme.txt` 是否按平台要求补齐。

## 2. 赛题 19 的官方核心问题

官方参赛指南中，赛题 19 属于“揭榜挂帅”赛道四“多模态技术与数据治理”，发榜单位为华泰证券，赛题名称是“行情选股 DSL 到高性能 Doris SQL 的自动化编译系统”。核心研究问题是：如何将行情选股领域专用语言 DSL 自动编译为高性能 Doris SQL，实现选股策略的高效执行。

这句话可以用人话解释为：前端、分析师或智能问答系统已经能把选股想法变成一种 DSL，但数据库不能直接执行 DSL。项目要做的是中间那座桥，把 DSL 稳定、准确、高性能地翻译成 Doris SQL。这里的“高性能”不是宣传词，而是要在 19 年或 20 年跨度的行情数据上，用前缀和、物化视图、分区裁剪等方法让查询明显快于普通全表扫描。

当前项目的对应实现是 `Compiler.compile()` 作为总入口，依次经过 lexer、parser、semantic analyzer、SQL generator、Doris SQL validator 和 explain 事件记录。对于正确性，项目引入 Pandas reference evaluator 和 SQLite executor 做结果集等价验证；对于性能，项目保留 Doris 5,000,000 行证据，显示 120 日成交量滚动 SUM 的 prefix 优化路径达到 `36.24x` 加速。

## 3. 官方技术攻关问题与当前项目对应

官方题面提出的第一个难点是“语义理解的完备性与高维嵌套解析”，包括 `then`、`CONS/EXIST`、跨市场位运算 `|&^`、强类型约束和标准 AST。当前项目已经有 lexer、parser、AST node、semantic analyzer，并通过官方风格正负例套件覆盖主干语义。需要注意的是，官方题面提到“全量 12 类领域函数”，但你当前提供的 TXT 没有列出完整 12 类函数清单，因此正式说法应是“覆盖主要领域函数和官方风格样例，完整 12 类需拿到 DSL 规范后逐项复核”。

官方题面提出的第二个难点是“异构语义间的等价重写与组合爆炸”，要求把 `then` 改写为多阶段 CTE，把 `CONS` 改写为窗口函数，把区间条件动态转成混合开闭区间 SQL，并保证数学等价。当前项目的 `sqlgen.py` 承担这部分工作，`reference.py` 和 `equivalence.py` 用独立结果集验证防止 SQL 生成器自说自话。答辩时可以这样讲：我们不是只检查 SQL 字符串，而是比较 DSL reference 结果和 SQL 执行结果，missing/extra 都为空才算通过。

官方题面提出的第三个难点是“业务逻辑与编译内核的解耦管理”，例如复权因子选择、成分股索引映射、表名映射等业务规则要从代码里剥离。当前项目用 `configs/indicators.json`、`configs/tables.json`、`configs/functions.json` 和 `registry.py` 承接配置化能力。新指标扩展已有 config-only evidence；本轮新增 `ABS` 模板函数后，简单数值函数也能通过 `sql_template` 和 `reference_op` 接入 SQL 生成与 reference 验证。复杂时序函数仍然涉及窗口语义、Doris 优化路径和更多边界测试，不应在答辩时说成任意函数都已经完全零代码。

官方题面提出的第四个难点是“极长周期查询的自适应路由与加速”，面对 19 年以上历史跨度，普通全表扫描不可行。当前项目针对 rolling SUM 的长窗口场景实现 prefix-sum rewrite，并保存了 Doris evidence。这个证据非常有价值，但要带着边界讲：它证明 5,000,000 行 Doris 数据、120 日成交量滚动 SUM、prefix 热点路径达到了超过 10x 的目标；它不证明所有函数、所有窗口、所有机器都有同样加速。

## 6. 答辩时最稳的表达

可以这样概括当前项目：FinDSL Forge 面向华泰证券赛题 19，目标是把行情选股 DSL 自动编译为高性能 Doris SQL。系统采用受控 DSL、确定性编译器、语义校验、Doris SQL 安全验证、reference 等价验证和 prefix-sum 长窗口优化，避免大模型直接生成 SQL 带来的不可控风险。当前证据显示，项目已有 `197 passed` 自动测试、官方风格正例和负例均为 `37/37`、readiness blocking gates `PASS`、warning count `0`，并在 5,000,000 行 Doris 数据上取得 `36.24x` 长窗口加速。

同时也要自然补一句边界：当前 `36.24x` 是特定长窗口 SUM 路径的真实 Doris 证据，不泛化所有查询；新指标配置化已经实现，简单数值函数模板也已有 `ABS` 证据，复杂时序函数仍需继续模板化；官方“12 类领域函数”和官方 20 年数据集到位后，会按官方规范继续逐项补充验证。这种讲法不但不会显得项目弱，反而说明你理解工程证据的适用范围。
