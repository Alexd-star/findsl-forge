# 03 核心算法与代码调用链

## 1. 项目的核心算法是什么

这个项目不是单一算法，而是一条“金融 DSL 编译与验证流水线”。最核心的部分有四个：

1. DSL 编译算法：把 DSL 解析成 AST，再生成 Doris SQL。
2. 语义校验算法：判断指标、函数、参数、窗口是否合法。
3. prefix-sum 长窗口优化：把长窗口滚动求和改写为前缀表查询。
4. SQL/reference 等价验证：用独立 reference oracle 检查 SQL 结果是否正确。

答辩时不要只说“用了 AI”。更稳的说法是：

> 项目核心是一个确定性的金融 DSL 编译器。AI 或中文输入只提供候选 DSL，所有候选都必须通过语法、语义、安全 SQL 校验和 SQL/reference 等价验证。长窗口性能通过 prefix-sum 和 Doris 证据证明。

## 2. 编译器主流程

### 2.1 所在文件和函数

| 内容 | 文件 | 函数/类 |
|---|---|---|
| 编译器入口 | `src/findsl/compiler.py` | `Compiler.compile()` |
| 语法解析 | `src/findsl/parser.py` | `parse()`、`Parser.parse()` |
| 语义校验 | `src/findsl/semantic.py` | `SemanticAnalyzer.validate()` |
| SQL 生成 | `src/findsl/sqlgen.py` | `SqlGenerator.generate()` |
| SQL 安全校验 | `src/findsl/doris_sql.py` | `validate_doris_select_sql()` |

### 2.2 输入、输出和关键变量

输入是 DSL 字符串，例如：

```text
filter(indicator("close") > 10)
```

输出是 `CompileResult`，主要字段包括：

| 字段 | 含义 |
|---|---|
| `dsl` | 原始 DSL |
| `ast` | 抽象语法树 |
| `sql` | 生成的 Doris SQL |
| `trace` | 人可读的优化/重写路径 |
| `explain` | 机器可读的优化说明 |
| `elapsed_ms` | 编译耗时 |

### 2.3 处理步骤

`Compiler.compile()` 的处理步骤很清楚：

1. `parse(dsl)`：把 DSL 变成 AST。
2. `SemanticAnalyzer.validate(ast)`：检查 AST 是否语义合法。
3. `SqlGenerator.generate(ast)`：生成 Doris SQL。
4. `validate_doris_select_sql(sql)`：检查 SQL 是安全的 Doris 查询。
5. 返回 `CompileResult`。

如果任何一步失败，就抛出错误。比如指标写成 `clos`，语义校验会报未知指标，不会继续生成 SQL。

## 3. SQL 生成算法

### 3.1 所在文件

SQL 生成集中在：

```text
src/findsl/sqlgen.py
```

核心类是：

```text
SqlGenerator
```

### 3.2 主要函数

| 函数 | 作用 |
|---|---|
| `generate()` | SQL 生成总入口 |
| `_relation_sql()` | 判断顶层是 filter、rank、then 还是普通条件 |
| `_filter_sql()` | 生成筛选 SQL |
| `_rank_sql()` | 生成每日排名 SQL |
| `_bool_sql()` | 把布尔条件翻译成 SQL |
| `_numeric_sql()` | 把数值表达式翻译成 SQL |
| `_register_numeric_window()` | 注册需要先物化的窗口特征 |
| `_try_register_prefix_sum()` | 尝试把 SUM 改写到 prefix 表 |
| `_date_pushdown_kind()` | 判断日期过滤能否下推 |
| `_explain()` | 记录优化证据 |

### 3.3 关键变量

| 变量 | 含义 |
|---|---|
| `required_tables` | 当前查询需要哪些表，例如行情表、资金流表、股票市场表 |
| `trace` | 人可读的重写说明 |
| `explain` | 结构化优化步骤 |
| `_numeric_features` | 需要先算出来的数值窗口特征 |
| `_rolling_features` | 需要先算出来的滚动布尔特征 |
| `_current_source` | 当前查询阶段的来源表或 CTE |

### 3.4 边界情况

SQL 生成必须处理以下边界：

1. 窗口函数不能直接放在 `WHERE` 中，要先放到特征层再过滤。
2. 日期范围过滤遇到窗口函数时不能简单下推全部日期，否则会截断历史窗口。
3. `rank(percent=...)` 要按每日分组数量计算百分比阈值。
4. 稀疏资金流表不能让交易日错位，所以 reference 和 prefix 表都基于 daily_quote 的交易日骨架。
5. 支持 prefix-sum 的指标才走 prefix 优化，不支持的指标仍走普通窗口函数。

## 4. Prefix-sum 优化算法

### 4.1 算法目的

长窗口滚动求和很慢。比如每只股票每天都要算“过去 120 天成交量之和”，普通窗口函数需要对大量行做重复计算。prefix-sum 的思想是提前把累计值或指定窗口结果准备好，查询时直接读取或做差。

项目里的关键证据是：

```text
filter(SUM(indicator("volume"), 120) > 1000000)
```

在 Doris 证据中，baseline 窗口查询平均约 5182 ms，优化后约 143 ms，加速约 36.24x。

### 4.2 所在文件和函数

| 文件 | 函数 | 作用 |
|---|---|---|
| `src/findsl/sqlgen.py` | `_sum_can_use_prefix_lookup()` | 判断某个 SUM 能不能走 prefix |
| `src/findsl/sqlgen.py` | `_try_register_prefix_sum()` | 注册 prefix-sum 特征 |
| `configs/indicators.json` | 指标配置 | 声明某指标是否支持 prefix-sum |
| `configs/tables.json` | 表配置 | 声明 prefix 表 |
| `deploy/doris/03_build_prefix_tables.sql` | Doris SQL | 构建 prefix 表 |

### 4.3 简单样例手工演示

假设某只股票连续 5 天成交量是：

| 日期 | 成交量 |
|---|---:|
| 第1天 | 10 |
| 第2天 | 20 |
| 第3天 | 30 |
| 第4天 | 40 |
| 第5天 | 50 |

如果要算 3 日滚动求和：

| 日期 | 普通算法 | 结果 |
|---|---|---:|
| 第1天 | 10 | 10 |
| 第2天 | 10+20 | 30 |
| 第3天 | 10+20+30 | 60 |
| 第4天 | 20+30+40 | 90 |
| 第5天 | 30+40+50 | 120 |

prefix-sum 先算累计值：

| 日期 | 累计成交量 |
|---|---:|
| 第1天 | 10 |
| 第2天 | 30 |
| 第3天 | 60 |
| 第4天 | 100 |
| 第5天 | 150 |

第5天的 3 日和可以用：

```text
第5天累计值 150 - 第2天累计值 30 = 120
```

如果 Doris 表中已经有 `volume_sum_120` 这类物化列，那么查询时甚至不用做差，直接读取对应列。项目证据里的 120 日成交量路径就是为了展示这种长窗口加速价值。

## 5. SQL/reference 等价验证算法

### 5.1 所在文件和函数

| 文件 | 函数 |
|---|---|
| `src/findsl/equivalence.py` | `verify_sql_equivalence()` |
| `src/findsl/reference.py` | `PandasReferenceEvaluator.evaluate()` |
| `src/findsl/executor.py` | `SQLiteSampleExecutor.execute()` |

### 5.2 算法目的

SQL 生成器可能写错 SQL。为了不让它“自己证明自己正确”，项目另外写了一套 Pandas reference evaluator。它直接解释 DSL，不依赖 SQL 生成逻辑。然后项目把两边结果的 `(ts_code, trade_date)` 做集合比较。

### 5.3 输入和输出

输入：

```text
DSL
data/samples/ 里的 CSV 数据
```

输出：

| 字段 | 含义 |
|---|---|
| `passed` | 是否完全一致 |
| `sql_keys` | SQL 查询得到的股票和日期 |
| `reference_keys` | reference 得到的股票和日期 |
| `missing_keys` | reference 有但 SQL 没有 |
| `extra_keys` | SQL 有但 reference 没有 |

### 5.4 手工理解

如果 reference 认为结果应该是：

```text
000001.SZ, 2024-01-03
600519.SH, 2024-01-03
```

SQL 执行结果也是这两行，那么：

```text
missing_keys = []
extra_keys = []
passed = True
```

如果 SQL 少了一行，就会出现 missing；如果 SQL 多了一行，就会出现 extra。这比只看 SQL 字符串更可靠。

## 6. 诊断和安全边界

项目特别强调错误输入不能失控。相关文件包括：

| 文件 | 作用 |
|---|---|
| `src/findsl/diagnostics.py` | 把异常转换成错误码和修复建议 |
| `src/findsl/doris_sql.py` | 检查 SQL 是否安全 |
| `src/findsl/llm_adapter.py` | 拒绝直接 SQL 和错误 DSL |
| `data/samples/official_negative_cases.jsonl` | 负例题库 |

例如用户输入：

```text
filter(indicator("clos") > 10)
```

`clos` 不是配置里的合法指标。系统应返回 `UNKNOWN_INDICATOR`，而不是生成错误 SQL 或崩溃。答辩时可以展示 Web Demo 的负例截图，说明系统有错误恢复能力。
